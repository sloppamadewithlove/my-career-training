Native training clocks and ball visibility — research synthesis
27 October 2026

What the source establishes
The generated native declarations distinguish Tutorial and TrainingEditor events.
Both share Soccar ancestry: Tutorial -> Soccar; TrainingEditor -> GameEditor ->
Soccar. The public SDK mirrors this with TutorialWrapper -> ServerWrapper and
TrainingEditorWrapper -> GameEditorWrapper -> ServerWrapper. Therefore the editor
does inherit the common clock getters. A different immediate parent does not imply
a different clock implementation or make GetGameTimeRemaining invalid by itself.

The training UI data has distinct SetTrainingGameEvent(Tutorial) and
SetTrainingEditorGameEvent(TrainingEditor) methods, along with type, difficulty,
current/total round, tip and progress data. This supports observing the mode before
interpreting its state. Exact instantiated classes for each current menu choice
remain a runtime check; generated signatures do not prove that mapping.

Useful declared public observations
- Common: GetGameTimeRemaining, GetSecondsRemaining, GetWaitTimeRemaining,
  GetbRoundActive, GetbUnlimitedTime; game-state and replicated game-state clocks.
- Tutorial: GetEventStartTime, GetDifficulty, GetGameEventRounds, GetWaveIndex,
  GetRedoCount/GetRedoTotal, plus UI round/tip/progress getters.
- TrainingEditor: configured MinRoundTime/MaxRoundTime, shot attempt, playtest type,
  and inherited GameEditor active round. Limits are not live countdown readings.
- Ball: presence first, then GetbFadeIn/GetbFadeOut/GetbEndOfGameHidden and geometry.
  Actor hidden state is another declared observation. Flags and visual disappearance
  must be correlated; an object can exist while not visibly rendered.

The generated event names provide specific research leads: common game-time update,
ball reset/spawn, tutorial round finished, and editor round-time/round-attempt/reset.
These are not recovered event order or function implementations. ResetRoundTime,
FadeOutBall, FadeInBall and setters are mutations, not observer reads.

Next useful experiment
Use the existing scoped observer after native-entry repair and a fresh owned-game
handoff. Compare the raw clock with the displayed shot timer at setup, first input,
active shot, timeout, retry, next shot and exit. If it does not match, add the other
declared clock readings through a separate reviewed observer change. Capture ball
presence/fade/hidden and visible behavior together. Prove that retry restores the
ball and all scenario actors. Do not infer function causation from polling.

The current reviewed observer records only one raw clock, presence, fade-out,
end-hidden and round state. Other fields above are research leads, not implemented
or tested observations. Third-party layouts must not be assumed to match this game
build; the proposed integration uses pinned public SDK accessors first.
