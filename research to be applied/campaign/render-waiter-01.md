## What the pinned source exposes

`BridgeHandler` calls `WaitForConnectionAsync()`, then enumerates `TcpMessenger.ReadAllAsync()` (`work/render-budget-reference-01/BridgeHandler.cs:54-63`). In normal clump processing it calls `ResetByteCount()` and `Rendering.ResetClearCount()` under `lock (_context)` (`:63-83`). In cleanup, while holding that same lock, it calls `Rendering.ClearAllRenders()` and loops on `SendRenderClears()`. A false result from `WaitForAnyMessageAsync().Result` breaks; true resets only byte accounting before the next iteration; exceptions are caught and messenger disposal is in `finally` (`:194-225`). `Main` constructs `TcpMessenger(gamePort)` and invokes `Cleanup()` from `finally` after `BlockingRun()` (`Main.cs:95-114`).

That caller gives only a **branch interpretation** of the wait result: false means “stop retrying”; true means “reset byte count and retry.” It supplies no cancellation token or timeout. The source does not specify whether the wait consumes a message, checks buffered data, waits for a socket read, returns false on closure, or returns true for any particular queued/incoming condition. Its return type’s boolean use is visible; the implementation is not.

`Rendering.SendRenderClears()` calls `_renderingCommandQueue.Send()` even when its clear-ID queue cannot advance (`Rendering.cs:244-255`). The source does not say whether that send can block, throw, or return before data is accepted. Cleanup catches exceptions and disposes, but if `Send()` blocks, execution has not reached the waiter yet. These outcomes cannot be resolved from the caller.

## Reachability conclusion

The static no-progress state remains conditional: if cleanup has pending IDs while the clear counter is 1,024, `_renderingCommandQueue.Send()` returns, and the waiter repeatedly returns true without an external `ResetClearCount()`, each retry leaves the clear queue unchanged. Normal clump reset is inside the same `_context` lock and cannot run concurrently while cleanup holds it. `BridgeHandler.BlockingRun()` waits on `Task.WhenAny(HandleInternalMessages, HandleServer)` (`BridgeHandler.cs:191-192`), so its return establishes that one loop task completed, not that both did. `Main` then calls cleanup from `finally`. This source confirms a caller path into cleanup, but does not show that a real shutdown reaches the overflowing state, that `Send()` returns, or that `WaitForAnyMessageAsync()` returns true repeatedly. Cleanup can instead complete without a pending queue, break on false, exit through an exception, or remain inside a blocking dependency call. No runtime hang claim is supported.
