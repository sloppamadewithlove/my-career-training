# ATTEMPT-END-01 — Power Shots after timeout or success

**Scope:** static trace of the frozen `work/reviewed-training` source after a Power Shots attempt becomes terminal, through result publication, retry/shot navigation, and Return. This does not establish live Rocket League ball motion. For setup, timer basis, and outcome chain, see [PHYSICS-01](physics-01.md).

## Finding

MCT has **no terminal ball/car visibility or physics write** in the traced Power Shots path. `TrainingEngine._finish()` marks the engine finished and records feedback (`src/my_career_training/training/engine.py:1181–1231`); the completed update emits a `completed` event (`engine.py:815–835`). The worker applies `adapter.desired_state()` only for `set_state` events, then publishes the result; after finish it continues telemetry/HUD work, but does not synthesize a terminal state (`src/my_career_training/game_worker.py:1303–1325`). The adapter's desired state is a whole-state write containing ball 0 and the Human plus configured bot cars (`src/my_career_training/adapter.py:167–203`), called on reset and situation replacement (`game_worker.py:630–643, 739–770`). No call to hide, park, freeze, fade, or respawn the ball/car was found on finish.

That absence only proves the app does not issue such a terminal write. It does **not** prove whether the Rocket League ball keeps moving, settles, or is acted on by native game behavior after a score/timeout. The player car is likewise not explicitly frozen by MCT. Scenario bots are an exception: in active match packets the worker sends neutral `PlayerInput` to configured scenario bots whenever the engine is not active, including after finish (`game_worker.py:1275–1288`). That is bot input control, not a ball or Human-car reset.

The timeout uses the scenario's active game-packet clock: `frame.time` comes from `match_info.seconds_elapsed` (`src/my_career_training/adapter.py:161`); non-Active match phases are excluded, while accepted active samples advance `active_elapsed` (`training/engine.py:580–615, 800–820`). At `active_elapsed >= lesson.timeout`, the engine finishes with `timeout`; scenario success can finish earlier. There is no separate wall-clock terminal cleanup.

## Result, HUD, and acknowledgement

The worker can call `publish_attempt()` twice on the terminal packet: once for the engine's `completed` event and once for `engine.finished`. `publish_attempt()` returns when that attempt ID was already sent, so the traced path emits one `attempt` event per attempt ID (`game_worker.py:1318–1323, 1374–1392`). The bridge sets `latest_attempt`, stores the summary/recording, then sends `attempt_ack` (`src/my_career_training/bridge.py:2086–2090`). The worker accepts only an acknowledgement matching `attempt_sent` (`game_worker.py:973–981`).

The native Power Shots card remains eligible while the session is still `training`; its model reads telemetry coaching, not `latest_attempt` or acknowledgement state (`plugin/include/TrainingLessonInput.h:350–416`). Thus it shows no “saving” or “ack pending” status. On timeout, coaching reports phase `finished` and remaining time 0; the card displays `TIME 0 / <limit>` and, when timing feedback is enabled, `Finished <elapsed>s`. On an early success, remaining time may be nonzero, so it displays `TIME <remaining> / <limit>` alongside `Finished <elapsed>s`. The instruction is generic coaching text (“Review the observed steps…” or “Drill target observed…”), not the scenario-specific observations from `_scenario_feedback()` (`training/coaching.py:66–74`; card rendering at `plugin/src/CareerUI.cpp:701–755`). The fallback RLBot overlay instead shows `Finished <duration>s` and generic coaching text (`game_worker.py:1411–1450`).

Scenario-specific attempt feedback can be shown in the Training page's “LATEST ATTEMPT” area (`plugin/src/CareerUI.cpp:399–400`), but it is not the top-left card's source. This is a visible feedback gap if the intended expiry behavior requires a prominent terminal result or a saving state.

## Retry, next situation, and Return

- **Manual retry:** rejected while `attempt_sent` exists and is not acknowledged (`game_worker.py:633–634`). Once allowed, `engine.reset()` returns a settling state that is sent through the whole-actor `desired_state`; controller and attempt/ack fields are reset (`game_worker.py:635–653`). This is the explicit path that writes a fresh ball and car setup.
- **Automatic retry:** on matching acknowledgement, if `auto_reset` is enabled and the result has a sample-backed recording, the worker schedules the normal reset for one second later to preserve feedback (`game_worker.py:973–981, 1378–1387`). The deadline is held during telemetry recovery; when due, it rechecks preference, ack, retryability, and stop/cancel state before calling `reset()` (`game_worker.py:888–903`).
- **Next/previous situation:** the worker rejects scenario navigation while `engine.finished` **or** any `attempt_sent` remains, even after acknowledgement, with “Save or retry the completed attempt before changing situations” (`game_worker.py:681–687`). A retry clears terminal state; then replacement setup is prepared and its whole-actor state is sent (`game_worker.py:739–800`). Shuffle only changes future order and does not reset the active shot (`game_worker.py:714–728`).
- **Return:** the native “LEAVE SESSION” action dispatches `return_hub` for training (`plugin/src/CareerUI.cpp:151–160`). Unlike retry, the bridge's `return_hub` branch has no `attempt_acked` guard; it starts the stop path when the worker is active (`src/my_career_training/bridge.py:1102–1154`). `_begin_stop()` changes session state to “Stopping Career” and sends `shutdown` (`bridge.py:2225–2238`), which makes the native training card inactive; worker rendering is also suppressed while stopping. Worker teardown calls `stop_match(shutdown_server=True)`, closes its relays, and recovers its map guard (`game_worker.py:1517–1537`); the bridge authorizes native Return after cleanup (`bridge.py:2240–2276`). These paths stop the owned session; they do not contain a ball-disappearance or terminal ball-reset action. Exact behavior if Return races with an attempt event not yet read by the bridge was not runtime-tested.

## Integration gap and acceptance target

To meet a requested “ball disappears when the in-shot timer expires” behavior, an implementation needs an explicit, owned expiry transition: decide whether it applies only to timeout or also success; define ball visibility/parking semantics and whether the Human car is untouched; publish a terminal phase/result and save-pending indication; and ensure Retry/next/Return restores or replaces the whole state exactly once. Current code proves reset ownership on retry/setup, but has no terminal ball action. Before acceptance, observe in an isolated offline Power Shots session that timeout visibly removes the ball, score-success behavior is intentional, a pending save does not prematurely reset it, retry produces the next configured ball/car state, next/previous is rejected until the documented condition, and Return stops ownership without leaving a stale overlay or controller. Source tracing alone cannot certify physics, overlay timing, or that acceptance behavior works in game.
