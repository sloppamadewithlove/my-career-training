# CAMERA-01 — Camera state, training bindings, and ghost input

## Scope and confidence

Static source review of `work/reviewed-training` plus the BakkesMod SDK headers pinned by `plugin/CMakeLists.txt` to `479e8f571cf554b25f4eeb64d611dec4133edcaf` (archive SHA-256 `e4072d2884a432bedfd7a7e8474000137b1649deeea3346de4f1b2a0cb9dd866`). Public behavior claims below use Rocket League/Psyonix, Epic, BakkesMod SDK, or the Controller Overlay Pro publisher’s page. No game input, process attachment, or runtime validation was performed. Source facts do not establish that a shipped plugin binary or a particular installed overlay version matches these sources.

## Camera ownership and preservation

- Targeted searches of current product `plugin/src`, `plugin/include`, and `src/my_career_training` found no production camera getter/setter call. The product currently stores `training_display.ghost_view` choices (`player/chase/side/top`) and labels them as camera/view options in `plugin/include/NativeCareerLayout.h:2451-2458`; the choice is accepted in `src/my_career_training/training/coach.py:33,69`. The coach’s `camera_control` field explicitly says “Target suggestions only; runtime camera support must be checked” (`coach.py:310`), while the native UI says camera perspectives require verified integration and the current ghost does not take car control (`plugin/src/CareerUI.cpp:666`). The setting is not evidence of an applied camera mode; no current consumer was found that calls a camera API.
- The game’s documented personal camera settings include FOV, height, angle, distance, stiffness, swivel speed, shake, and the ball-cam indicator ([Epic support: “What are camera settings in Rocket League?”](https://www.epicgames.com/help/c-37599050/c-32343914/what-are-camera-settings-in-rocket-league-a14443106?lang=en)). Rocket League’s Sep. 18, 2026 Season 24 article also announces a Free Look camera that can be enabled for controllers ([official Season 24 announcement](https://www.rocketleague.com/news/rocket-league-heads-to-the-streets-in-season-24), lines 20-21). These are player-owned settings and camera controls to preserve.
- The pinned SDK declares `GameWrapper::GetCamera()` and `CameraWrapper::GetCameraSettings()` / `SetCameraSettings()` (and camera state/location methods). Those are available declarations, not proof of safe runtime behavior ([pinned GameWrapper.h](https://github.com/bakkesmodorg/BakkesModSDK/blob/479e8f571cf554b25f4eeb64d611dec4133edcaf/include/bakkesmod/wrappers/GameWrapper.h#L75), [pinned CameraWrapper.h](https://github.com/bakkesmodorg/BakkesModSDK/blob/479e8f571cf554b25f4eeb64d611dec4133edcaf/include/bakkesmod/wrappers/GameObject/CameraWrapper.h#L21-L22)). A future camera adapter could snapshot and conditionally restore through these declarations, but no such path exists now.
- `retry_lesson` calls `GameWorker.reset()`, which resets the lesson engine/scenario and sends its desired RLBot state (`src/my_career_training/bridge.py:1429-1434`, `game_worker.py:615-649`). This code does not snapshot or write camera settings. Return-to-hub stops the worker (`bridge.py:1127-1145`); the plug-in releases temporary input bindings and restores the external controller overlay when scope ends, but does not restore camera state (`plugin/src/MyCareerTraining.cpp:1415-1424`). Whether Rocket League itself changes camera mode/settings during lesson entry, retry, or Return is **unobserved**.

The lesson bind guard snapshots previous bind strings, verifies its own bind writes, and on release restores a key only if the current string is still the command it installed (`TrainingLessonInput.h:244-315`). This avoids overwriting a later user edit. The UI’s lesson HUD advertises fixed D-pad shortcuts; Reset uses the existing game binding and Ghost is “PAUSE MENU ONLY” (`CareerUI.cpp:740-750`). The “Input labels” selector states that it changes labels only (`NativeCareerLayout.h:2467-2479`); it is not a lesson key remapper.

### Custom Training and mode conflict

Psyonix’s official v2.16 patch notes (June 14, 2022) document stock Custom Training’s Next/Previous Shot, Select Shot, Shuffle Shots, and Shot Mirroring controls, and say those inputs are configurable under Settings → Controls → View/Change Bindings ([official v2.16 notes](https://www.rocketleague.com/news/patch-notes-v2-16-season-7-update), lines 28-46). This establishes that Rocket League has player-configurable training shortcuts; it does not prove their exact key defaults or whether BakkesMod’s bind string shadows the in-game mapping.

The product lesson guard checks owned/fresh/offline/foreground/in-game/training state, pause/replay/online/match-ended, native menu, reference capture, and Power Shots lesson ID (`TrainingLessonInput.h:154-166`; host scope in `MyCareerTraining.cpp:1214-1228`). It does **not** ask `IsInFreeplay()` or `IsInCustomTraining()`. Those SDK predicates exist ([pinned GameWrapper.h](https://github.com/bakkesmodorg/BakkesModSDK/blob/479e8f571cf554b25f4eeb64d611dec4133edcaf/include/bakkesmod/wrappers/GameWrapper.h#L53-L55)); the career team-lock path explicitly checks both, but lesson-input eligibility does not (`MyCareerTraining.cpp:1471`). Therefore source confirms an unguarded coexistence risk, not observed breakage. Verify that custom training’s own configurable controls, freeplay controls, and user bind strings remain usable whenever this lesson scope activates.

The separate `TrainingGhostInput` helper describes an XInput D-pad toggle, but no production `plugin/src` call site references it; treat it as an unused model, not an active shortcut (`plugin/include/TrainingGhostInput.h:1-31`). Current UI/service controls use explicit ghost commands, and the native HUD says Ghost is pause-menu only (`CareerUI.cpp:437-446,740-750`).

## Requirements for player-visible behavior

1. State whether an overlay shows raw physical device buttons, game-resolved logical actions, or recorded coach actions; never blend these labels.
2. Show the actual owned lesson shortcuts and whether they temporarily replace any key binds. Make the controls configurable or clearly label fixed D-pad usage; never imply the “Input labels” profile remaps gameplay.
3. Preserve the player’s camera profile, current camera state, and Free Look/control settings across lesson launch, retry, Return, cancellation, and plugin/service loss. If capture/restore cannot be verified, leave the camera untouched and mark ghost view as a suggestion.
4. Explain that recorded ghost controls illustrate recorded logical actions under a display mapping, not the learner’s raw button presses.
5. On conflicts or unavailable/unmatched overlay state, show a clear unavailable state and retain Rocket League’s own controls and camera.

## Six future acceptance gates

1. **Launch:** Snapshot only the camera fields/mode the adapter owns; verify view is unchanged unless the player explicitly enabled a camera aid. Snapshot D-pad bind strings before any override.
2. **Shortcut truth:** With default and custom Rocket League bindings, shown lesson prompts match the actual shortcuts; no action is double-triggered; user’s original binds remain recoverable.
3. **Mode boundary:** Test owned lesson, Freeplay, stock Custom Training, pause/menu, replay, and online. Lesson bindings activate only in the declared owned mode; stock training controls stay intact.
4. **Retry:** Retry resets the drill while preserving the user’s camera mode/settings, bind preferences, overlay preference, and controller identity; it does not move the player car through MCT input.
5. **Ghost/demo:** A recorded demonstration’s displayed controller values match its recorded logical actions, follow the selected mapping, and are explicitly distinguished from physical input. Camera targets change the real camera only after a separately verified opt-in path.
6. **Return/failure:** Return, stale bridge, focus loss, pause, unload, and write conflict disable lesson shortcuts and restore only values still owned by MCT; camera values remain/restored to the snapshot. Surface partial restoration or conflicting edits instead of silently overwriting them.

## Evidence versus unknowns

**Established by source/docs:** current camera preference is not applied through camera APIs; retry resets lesson/RLBot state but contains no camera save/restore; lesson navigation overrides four BakkesMod bind strings and polls named keys; the live overlay is an external CVar-controlled plug-in; recorded controller diagrams are derived from logical actions, not raw buttons; Psyonix documents configurable stock Custom Training shortcuts.

**Still untested/unknown:** how Rocket League/BakkesMod dispatch `XboxTypeS_DPad_*` under each controller remap, whether BakkesMod `setBind` affects stock Custom Training action mappings, overlay v1.0.7’s exact raw/logical source per element and installed-version match, whether the returned ghost controller model is rendered, and whether any game transition independently changes camera state.
