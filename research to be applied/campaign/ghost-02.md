# GHOST-02 — Synchronized car and ball demonstration requirements

Follow-up compatibility limit: [boost/resource research](boost-resource-reset-01.md) shows ordinary records have empty mutator metadata and no pad-cooldown history. Equal stored objects do not establish equal observed boost policy or bot-pressure context.


**Date:** 2026-10-27
**Scope:** Static source and public API research only. No game, rendering, controls, code, tests, or recording assets were used.

## Finding

Each accepted training sample already stores car pose, ball position/velocity, logical input, and packet-gap status under one relative `game_seconds` timestamp. Playback does not currently consume a ball track: it interpolates the car pose and sample-held actions, then draws a wireframe car. `GhostPractice` is deliberately restricted to car-only lessons because its player-relative offset would otherwise detach the car from the recorded ball. The capture format is a useful basis for a synchronized demo, but it does not yet support one.

No validated teaching trace is installed. Recorder defaults identify a private local-player attempt with distribution disabled; the development reference route creates an unevaluated private candidate. The reference validator checks supplied provenance/success/permission fields, but itself warns that imported claims need real-game validation. This is source/API evidence, not a claim that a demonstrated shot is validated or visually accepted.

## Current data flow and consumed fields

```text
RLBot GamePacket -> normalize same packet -> TrainingEngine/Recorder.append
                 -> timestamped car + ball + logical-actions sample
                 -> interpolate_pose(cursor) -> car pose + held actions only
                 -> ghost_lines -> RLBot 3D line rendering
```

- RLBot v5 GamePackets provide live ball and player positions/velocities at a documented 120 Hz. The project’s adapter reads packet `match_info.seconds_elapsed`, car physics/orientation, `last_input` logical controls, and ball physics in one normalized frame (`adapter.py:127-164`; `game_worker.py:1191-1206`). Those controls are game-reported logical values, not physical controller-button capture (`adapter.py:148-150`; `game_worker.py:1473-1490`). A 120 Hz source does not guarantee an uninterrupted recording: samples are actual observations, and the engine marks cadence gaps.
- `Recorder.append` uses a relative time origin from the first accepted frame. It stores car position, Euler rotation and velocity; ball position and linear velocity; logical actions; `packet_gap`; and game speed (`training/recordings.py:204-260`). The adapter makes ball rotation/angular velocity available, but the Recorder does not persist them. `observed_start` saves the first observed car and ball state; `metadata.starting_state` separately describes the authored desired setup.
- There is no separate fixed-rate resampling pass. `interpolate_pose` locates bracketing sample times on demand, linearly interpolates car position, converts car Euler rotation to quaternions and SLERPs orientation, and holds the earlier sample’s actions. It refuses extrapolation and returns no pose across a span over 0.1 seconds or marked packet gap (`recordings.py:280-329`). Ball position and velocity are not returned or interpolated.
- `GhostPlayback` already owns a shared cursor with watch/lead modes, pause/resume, seek, speed, loop, restart, and stop. Watch advances from game time; lead is tied to attempt elapsed time. Its snapshot calls `interpolate_pose`, then derives only car lines and coach actions (`coach.py:137-312`). `GhostPractice` loops at normal speed on game time, but offers only On/Off, anchors once to the player plus a 300-unit forward offset, and never follows the player thereafter (`coach.py:371-535`).
- `relative_placement` maps recorded car-relative movement into a new pose using a yaw-only rotation plus translation and forward offset (`recordings.py:350-404`). It has no ball input. Applying it only to car would change the car-to-ball relationship. Applying the same rigid transform to both tracks would preserve that relationship, but the translated ball would then be an offset demonstration, not the actual ball in the learner’s current scene.
- `practice_support` rejects lessons with ball-dependent targets/events, including contact, goal target, carry, flick, and reset acquisition (`coach.py:327-345`). Legacy car playback can still exist, but it is not a car+ball example. The renderer draws the ghost as 3D line segments and text; it creates no ghost actor and does not apply ghost `PlayerInput` (`game_worker.py:1406-1471`, `coach.py:290-312`).

## Scene identity, synchronization, and provenance

The current recording matcher compares lesson ID/version, variation, game/framework version, hitbox, map, mutators, authored `starting_state`, and time base; unknown fields mismatch. It does **not** compare `observed_start`. Power Shots recording metadata has explicit `scenario_id`, `difficulty`, `scenario_version`, and `mirrored` fields, but `compatible_recordings` and `practice_context` do not include them (`recordings.py:145-172`; `engine.py:269-280`; `coach.py:348-368`). Initial-state equality alone should not be used as a durable substitute for those identifiers, especially for ranks that change only grading criteria (see CURRICULUM-01).

For a ball-dependent teaching demo, compatibility must include at least lesson/version/variant; explicit scenario or tier ID/version and mirrored state where relevant; map, mutators, game/framework build and hitbox; time base and speed policy; authored setup; and observed start car **and ball** state. Use a stable scenario/profile identity rather than comparing only numeric coordinates. A start-state tolerance, if one is ever allowed, needs to be specified and justified per scenario; no tolerance is established by this review.

A valid synchronized frame contract is one record per packet time with car pose, ball center, optional ball velocity, observed logical actions and one shared gap marker. Evaluate car and ball at the same playback cursor and same bracketing indices. Interpolate ball center linearly only within contiguous, finite samples. Do not extrapolate or use predicted-ball slices as though they were an observed reference. For a ball-dependent reference, missing ball fields or an invalid interval should hide the **paired car and ball depiction and its coach-input state** for that interval, with an explicit gap message. Do not silently keep a car pose while its paired ball track is unavailable. Sphere orientation is not currently stored; a simple position marker does not need it, but a rotation/spin display would need additional recorded fields.

For shot lessons, the safest first mode is exact world-space replay against an exact compatible reset/setup: car, ball, and path share the captured world coordinates. If a side-by-side/player-offset mode is desired later, apply one fixed rigid yaw+translation transform to both car and ball, preserve their relative geometry, and label it as offset. Do not use the existing car-only `forward_offset` for a ball drill. After Retry, current code restarts `GhostPlayback`, but `GhostPractice` anchors to the intended reset car pose immediately after sending the reset state (`game_worker.py:615-667`); a synchronized demo should wait for observed reset/setup state (especially ball launch position/velocity) before displaying or re-anchoring.

Reference validation currently requires `source.kind == actual_execution`, explicit distribution permission and basis, nonempty success evidence, success outcome, an untruncated capture, and known compatibility fields. Those are supplied metadata checks, not independent verification (`recordings.py:98-120`). The local Recorder defaults to `source.kind=local_player` and `permission.distribute=false` (`recordings.py:204-224`); the project reports no installed validated reference (GHOST-01; `training/coach.py:110-134`). A successful outcome proves only that the current engine criteria passed for that setup. CURRICULUM-01 records that some lesson success predicates do not require all steps of the named mechanic, so success is not expertise or rank calibration. Keep a personal best labeled as the player’s own attempt.

`compare_attempts` currently reports event-time differences only. It requires compatible context, ignores uncertain/coaching-suggestion events, uses the first accepted occurrence of each matching event name, and returns a time difference plus an uncertainty interval; it computes no pose, ball-path, action-sequence similarity, skill grade, or expert score (`recordings.py:461-507`). It does not itself require `require_reference=True`, so any caller offering a “reference comparison” must gate on independently reviewed provenance and success. Present observed deltas as timing observations, not a target script or proof one successful technique is mandatory.

## Rendering APIs and boundaries

The project pins `rlbot==2.0.0b56` and `rlbot-flatbuffers==0.19.0`; its worker uses RLBot’s `Renderer` and 3D line calls (`pyproject.toml:13-16`; `game_worker.py:433-434,1406-1471`). The RLBot v5 Rendering guide declares `Line3D` for a 3D segment and `PolyLine3D` for a world-coordinate path, with PolyLine3D recommended as more efficient for a path. It documents renderer permission (`can_render`), fixed line width, 3D lines that do not shrink with distance, and render-message byte limits. The project requests `DebugRendering.OnByDefault` in its match configuration, but `game_worker.render` still skips drawing when `renderer.can_render` is false (`adapter.py:114`; `game_worker.py:1406-1408`). This supports a render-only trail/marker design, not actor creation or collision behavior. Preserve the existing gate and bound or decimate trajectory points; a missing render permission should visibly disable the overlay rather than imply the reference is playing.

The pinned public BakkesMod SDK’s `GameWrapper::RegisterDrawable` supplies a `CanvasWrapper` callback. `CanvasWrapper` exposes 2D screen-space `DrawLine`, text/texture primitives, plus `Project`/`ProjectF` for a world location to screen coordinates; the inspected header has no world-space 3D line or polyline method. It could support a projected HUD path only after projection, behind-camera, and clipping behavior are verified, but it is not equivalent to RLBot’s world-space trajectory renderer. Use Bakkes for native HUD/text integration; the existing RLBot renderer is the supported 3D path in this project. Header presence does not prove current installed-runtime compatibility.

## Smallest extension plan and artifact lifecycle

1. **Keep the current recording schema readable.** Add a versioned ball-track contract for future references: required finite ball position on every sample for ball-dependent lessons, optional finite velocity, same `time`/`packet_gap` as car/actions. Treat old recordings with missing ball fields as car-only; never fill with zero. A ball lesson must remain unavailable for them.
2. **Extend one interpolation result.** Reuse the existing cursor and bracketing/sample-time index. Return interpolated car pose, ball center/optional velocity, and sample-held logical actions from the same interval. Suppress every paired channel at invalid gaps; add no physics prediction or actor writes.
3. **Select one placement mode.** Use world coordinates for exact scenario demos. Only add a separately labeled rigid side-by-side transform when the same transform is applied to both tracks. Revalidate scenario/rank/version and observed start on load and after scenario changes; fail closed while preserving the prior selection if validation fails.
4. **Reuse existing transport.** `GhostPlayback` already implements pause/resume, seek, restart, rate and loop. Extend its snapshot/render data with the ball marker and sampled trajectory; keep both tracks on its cursor. `GhostPractice` currently has no seek/pause/reset controls, so do not imply those controls exist there. Reset should restart the same demo only after the new setup is observed; Next/Return must clear the previous track immediately.
5. **Render visual data only.** Draw the car, a distinct ball-center marker, and a bounded path with RLBot 3D render primitives. Keep render group/refresh behavior bounded. Do not create game actors, send `PlayerInput`, set ball/car state, or count a displayed ghost as a lesson event. On Off/stop/gap/Return, clear stale lines, ball marker and controller display together.
6. **Promote references explicitly.** A personal attempt stays private. An imported candidate remains unverified until a human process confirms the actual successful execution, exact scene/config, event evidence, provenance and distribution permission. Only then may a separate reviewed reference status enable teaching language. Keep event-time comparison separate from any calibrated grading system.

## Minimum future acceptance

- Import/load rejects missing ball fields, unknown or mismatched scenario/rank/version, incompatible environment, invalid start state, truncation, or permission/provenance failures without replacing the currently selected reference.
- A captured compatible shot yields car and ball positions from one timestamp and playback cursor. At normal speed, pause, seek, resume, restart, loop, and retry affect car, ball, and coach-input display together. A forced gap hides the pair and reports why; it never bridges/extrapolates.
- The exact-scene mode visually aligns the replay with the recorded setup; a translated mode applies one rigid transform to both tracks and is labeled offset. Rendering-disabled state reports unavailable. Return/Next clears all stale artifacts.
- Offline observation confirms the overlay is visual-only: no ghost actor, input injection, ball/car movement, contact, goal, score, or completion event comes from rendering. This is future runtime acceptance, not established by source inspection.
- “Teaching reference” appears only for a reviewed successful actual execution with recorded permission and compatible scene identity. Comparison reports only measured event-time deltas and uncertainty currently supported; it does not invent a path-similarity percentage, coach score, or expert rank.
