# INPUT-COLLISIONS-01 — training, menu, and Workshop input ownership

## Scope and confidence

Static source comparison of the frozen `work/reviewed-training` candidate and the local shipped-default inventory in `work/campaign/native-config-01.md`. I read the existing CAMERA-01, SETTINGS-01, and RESTORE-01 findings before tracing the current paths. No game input, runtime observation, build, or tests were performed. This report distinguishes source-declared defaults from the player's effective bindings and from unobserved game dispatch behavior.

## Important overlaps and boundaries

**D-pad is a genuine declared overlap with stock Custom Training.** The four MCT keys are the same named `XboxTypeS_DPad_Left/Right/Up/Down` controls used by shipped stock Custom Training defaults. While MCT Power Shots scope is active, `TrainingBindingGuard` captures the previous *BakkesMod* bind string, writes `mct_training_previous/next/shuffle/mirror`, verifies the new strings, and restores the previous string only when the current string still equals its own command (`TrainingLessonInput.h:244-304`; host adapters in `MyCareerTraining.cpp:1195-1213`). The four registered notifier callbacks are empty (`MyCareerTraining.cpp:194-197`); the MCT action actually comes from per-tick `IsKeyPressed` edge polling and bridge dispatch (`:1231-1259`).

This is not a complete conflict arbiter. Acquisition overwrites any preexisting BakkesMod bind rather than refusing or asking which feature should own it. While active, `acquire()` immediately returns true without rereading the bindings (`TrainingLessonInput.h:258-260`), so a third party can change a bind during the lesson and MCT will continue polling the key. On scope exit, changed values are preserved instead of overwritten. However, the previous values live only in memory. If an MCT command is still present at a subsequent plugin load, startup cleanup removes the recognized stale command without a durable copy of the displaced value (`MyCareerTraining.cpp:203-206`). Whether such a command survives a full game crash/restart is unverified; [RESTORE-01](restore-01.md) explicitly leaves host binding lifetime open.

There is also a multi-controller asymmetry: binding acquisition occurs before the XInput count check. With more than one detected XInput controller, the code leaves `pad.slot == -1` and performs no MCT action poll, but the D-pad BakkesMod binds remain acquired for the otherwise eligible lesson scope (`MyCareerTraining.cpp:1228-1245`; `TrainingLessonInput.h:35-45,74-79`). Whether this makes stock actions unavailable depends on live bind dispatch and remains untested.

Whether BakkesMod's `setBind` also suppresses or coexists with Rocket League's native `DefaultInput.ini` action dispatch is **not established** by these source files. The default config is layered on a base config (`native-config-01.md:11-14`), and the player's merged/custom bindings were not inspected. Therefore the evidence proves that the same D-pad controls are declared by both features and that MCT replaces the BakkesMod bind; it does not prove whether one physical press triggers stock shot navigation, MCT scenario navigation, both, or only one in a live game.

**Enter, Back, and retry are not bound by the current lesson shortcut.** The active MCT lesson binding arrays contain only D-pad directions. The names `mct_training_retry` and `mct_training_ghost` occur as legacy strings considered during startup cleanup, not as current registered commands or current bindings (`TrainingLessonInput.h:247-250`; `MyCareerTraining.cpp:194-206`). MCT does not install an Enter, Escape/B, Backspace, or right-shoulder retry bind. Stock `ResetTraining` and stock shot-select defaults therefore have no source-level MCT bind replacement. In an active MCT menu, Enter/Cross and Back/Circle are menu navigation, but lesson input is gated out while that menu/pause is active.

**Ghost input is not an active competing shortcut.** `TrainingGhostInput.h` is referenced by its isolated tests, but no production call site was found in `plugin/src`; the current ghost controls come from menu/bridge actions, not a live D-pad toggle. Do not treat its tested helper model as a shipped input owner.

## Workshop and mode uncertainty

The ordinary Workshop session shape is `kind == workshop`, which cannot satisfy the lesson's exact `kind == training` requirement. The source also contains a separate native Workshop development route restricted to an owned Steam frontend and explicitly not game-tested or production-allowed. Neither route declares a map-control bind. A Workshop map may define controls or use Rocket League defaults, but the mapping and event routing of any selected map were not recovered here. The important remaining collision case is a game mode transition that occurs while an MCT Power Shots worker session remains marked active: because the lesson scope uses `IsInGame()` but does not exclude Freeplay/Custom Training, this predicate alone does not establish separation after such a transition. Whether that eligible-worker/mode combination is reachable through the complete game-worker lifecycle is unverified.

## Missing capability contract for toggleable mods

The current input path has no published per-feature ownership contract or user-facing input toggle. For any future toggleable training/mod feature, publish a machine-readable capability record containing:

- feature id and the exact activation/deactivation predicate (game context, menu/pause, worker/session identity);
- input source (`GameWrapper` named-key polling, raw device, native menu event, or BakkesMod bind), action per key, and whether it is configurable;
- keys/actions claimed in each context, plus known stock/other-mod overlaps;
- any bind/CVar writes, captured prior state, readback, restore condition, and crash-recovery limit;
- exclusivity/dependency rules and the player's selected owner when capabilities conflict.

Do not silently replace an existing mod bind when another active capability declares the same key/context. Offer an explicit choice or keep the feature off, and expose the current owner/reason in the UI. The existing `binding_profile` must remain labelled as prompt mapping unless it starts changing actual control ownership.

## Focused future acceptance: one press, one action

On an explicitly owned offline build, instrument one physical D-pad-right press and record the game mode, effective binding, MCT eligibility, BakkesMod bind before/after, stock training event, MCT bridge command/ack, and final shot/scenario index. Repeat with: (1) active MCT Power Shots; (2) stock Custom Training with no MCT worker; (3) the MCT-launched featured pack; (4) the MCT pause menu open; and (5) a selected Workshop map. Each press should produce exactly the one declared action for that context, with no hidden second action. Add a mode-transition case—enter Freeplay/Custom Training while the Power Shots worker remains active—and require lesson shortcuts to release or the UI to request a deliberate exclusive owner. Finally verify that Back/Enter and ResetTraining still perform their native operation once, that a user's custom bind is restored on normal exit, that a change made during the lesson is preserved, and that restart recovery cannot strand a dead MCT bind without an actionable notice.

## Evidence limits

This is source-level routing evidence, not runtime dispatch proof. `DefaultInput.ini` supplies defaults rather than the effective user map; native key-event propagation between Rocket League, BakkesMod binds, MCT polling, and other plug-ins is unobserved. No Workshop map controls were inspected. No compatibility claim is made about installed plug-in binaries or an active production version of the native Workshop trial.
