# REPLAY-IMPORT-FEASIBILITY-01 — native replay import as a personal demonstration

**Scope:** Public-source parser/API research and a read-only comparison with the existing MCT replay and recording contracts. No user replay, game process, account files, or third-party replay sample was opened or executed. This is static evidence, not a parser compatibility test against the installed game build.

## Finding

An opt-in, local **trajectory review** from a Rocket League `.replay` file is technically plausible with Boxcars. Boxcars exposes replay network frames, actor creation/deletion, timestamped actor-property changes, rigid-body position/orientation/optional velocities, player-replication links, and some match metadata. MCT would have to reconstruct persistent actor state across those updates. The result is replay-derived network telemetry, not the product's live RLBot packet capture.

It cannot currently satisfy MCT's complete recording/reference contract. Boxcars recognizes steer, throttle and handbrake properties plus replicated component activity and torque fields. These do not by themselves establish MCT's complete eight-channel `actions` record or raw button presses. MCT also requires a framework version and exact lesson setup identity that a normal RL replay does not record. Goals and aggregate statistics are available, but the inspected API does not supply a full authoritative timeline for MCT's mechanic events. Missing controls/events/setup must stay missing; they must not be inferred from the motion trace and presented as observed input or success evidence.

The safe first feature is a separately labeled **Personal Replay Import** that is read-only, private by default, and refuses to export a reference-eligible recording. It can show a paired car/ball path and replay clock only when the full network section parses and actor attribution is resolved. Controller hints and lesson scoring stay disabled unless the replay contains the exact required evidence and a future, separately reviewed schema explicitly supports that provenance.

## Parser identity and format risk

The candidate audited here is Boxcars **0.13.0**, released 2026-10-18. The `v0.13.0` tag points to commit [`370a0602a1fe95a8d4e70d67d5b95d825c4d3b63`](https://github.com/nickbabcock/boxcars/commit/370a0602a1fe95a8d4e70d67d5b95d825c4d3b63); its manifest declares **MIT**. The release change log lists Season 24/BladeBall support in 0.12.0, newer jump-count and product attributes in later releases, but does not claim compatibility with every future replay build. The Boxcars README explicitly says network data changes with Rocket League patches and defaults to returning header data even when network decoding fails. Therefore an importer must demand a complete network parse (`must_parse_network_data`) and reject a result with no `network_frames`; header-only success is not a usable trajectory. Version 0.13.0 has not been tested here against a replay from the installed game.

Boxcars is a low-level parser, not a high-level MCT adapter. Its source documents that the consumer must resolve actor `object_id` and `name_id` through the replay's object/name tables. Actor IDs can be reused after deletion, so any reconstruction must use lifetimes rather than treating the numeric ID as globally stable. The crate intentionally keeps flexible header properties as a vector because duplicate keys may exist.

## Capability crosswalk

| Requested field | Evidence in Boxcars 0.13.0 | What MCT can safely use |
|---|---|---|
| **Synchronized car and ball pose** | Network `Frame` carries `time`, `delta`, new/deleted actors and updated attributes. The mapped `TAGame.RBActor_TA:ReplicatedRBState` decodes to position, quaternion rotation, optional linear velocity and optional angular velocity. Car and ball actors share each network-frame clock. | Reconstruct both tracks on the replay clock by replaying updates and retaining each actor's last known state. Convert quaternion to MCT's Euler convention only through a tested conversion. These are network-sampled updates, not a complete per-packet trajectory; any held/interpolated poses must be labeled derived. Missing or optional values remain missing. |
| **Actor identity and player** | New actor records provide an actor ID, object/class index and optional name index. The recognized attributes include Pawn→PlayerReplicationInfo and PRI player name, unique ID and team. The PRI also has loadout fields. | Car-to-player mapping is reconstructable in principle by following actor references and respecting create/delete/reuse. It needs a bounded implementation and ambiguity rejection. Player identity is not automatically “the local human”; require the user to select a roster entry. Names, platform IDs, account identifiers and replay paths are private data. |
| **Car body / hitbox** | PRI client-loadout fields and product IDs can be present; actor class names and item products are raw replay metadata. No normalized MCT `car_hitbox` field is defined by Boxcars. | A curated, versioned product-to-body/hitbox mapping might recover the body for some records. Unknown, absent, anonymized or unmappable loadouts must fail exact-match checks. A replay's cosmetic IDs alone are not a guaranteed hitbox value. |
| **Actual actions** | The Boxcars attribute table includes `Vehicle_TA:ReplicatedSteer`, `ReplicatedThrottle` (byte values), and `bReplicatedHandbrake` (boolean). It does not expose one complete `PlayerInput`/`last_input` object; the recognized-property list does not provide MCT's full `throttle, steer, pitch, yaw, roll, jump, boost, handbrake` set. | At most, preserve the channels explicitly present, with raw parser value and provenance. Do not synthesize missing jump/boost/air-roll/pitch/yaw from kinematics, fill defaults, or show a complete controller ghost. These are game-replicated values, not raw physical-button presses. |
| **Clock / gaps** | Network frames contain seconds-valued `time` and a `delta`; separate replay keyframes contain time/frame/byte position. Actor attributes update sparsely. | Keep source frame number/time and original delta. A derived irregular-interval warning may mark a replay-timeline discontinuity, but it is not RLBot's `packet_gap` and does not prove packet loss. Do not resample to 120 Hz and call those invented samples observed. Store a replay-specific time base, not MCT's `game_seconds`, unless a conversion is independently validated. |
| **Build / map / mutators / setup** | Replay model exposes major/minor/network versions, flexible header properties, level names, object/package lists and keyframes. README's header example includes `BuildID`; docs say header properties include date/level and goal/player summary. A private-match settings attribute can include a mutator string; game-replication attributes include playlist/mutator indices. | Build ID and level names may help identify an environment. They do not prove the exact installed custom-map bytes/geometry. Private-match mutators are partial mode-specific metadata; an index is not a normalized full mutator set. No MCT lesson/rank/scenario version or authored `starting_state` is supplied. Exact compatibility often remains unknown. |
| **Authoritative events** | Header properties include goal scorer/time and player statistics; replay tick marks mark significant events such as goals but are positioned before event onset for highlight lead-in. Network attributes contain stat counters (including match flip resets) and a low-level stat-event record with an object ID. | A goal/score summary may validate a match outcome; a tick mark is not the exact goal time. Aggregate reset/touch stats are not per-shot event traces. The inspected surface does not establish MCT's ordered mechanic events (touch/reset acquisition/carry/flick/target) or lesson-specific success. Geometry-derived contacts would be inference, not authoritative evidence. |

The public source anchors are `src/models.rs` (Replay/header/keyframe/tickmark shapes), `src/network/models.rs` (network Frame, actor references and spawn state), `src/network/attributes.rs` (RigidBody, PrivateMatchSettings, StatEvent), and `src/data.rs` (recognized PRI, ball, vehicle, game-event and input attributes). The README describes header-vs-network parse behavior and an example `BuildID`; the parser's network mode permits strict failure on a bad network section.

The recognized component fields include `CarComponent_TA:ReplicatedActive`, `ReplicatedActivityTime`, `Vehicle`, and `CarComponent_Torque_TA:ReplicatedTorqueInput` (`src/data.rs:149–152`). These are additional possible evidence for a separately validated decoder, not proof of absent jump/boost information. This pass did not resolve their component lifetimes, bit encodings, synchronization or equivalence to the live logical action channels. Consequently the limitation is an unestablished complete input reconstruction, not a claim that the replay contains only three useful control-related fields.

## Fit with the current MCT schema

The current schema is version 1 in `work/reviewed-training/src/my_career_training/training/recordings.py:35-96`. It requires `time_base == "game_seconds"`, a strictly increasing timestamp, oriented car pose, and all eight action keys in every sample. Ball position/velocity, angular velocity, wheel contact, boost, and gap markers are optional. Reference mode additionally requires `source.kind == "actual_execution"`, explicit distribution permission, nonempty success evidence, a successful outcome, an untruncated capture, and known game/framework/hitbox/map; it warns that imported claims still need real-game validation (`recordings.py:98-120`).

MCT's compatibility matcher compares lesson ID/version, variation, game/framework version, hitbox, map, mutators, configured starting state and time base (`recordings.py:145-172`). The Recorder's normal source is live local-player telemetry with distribution disabled (`recordings.py:204-224`). Its sample is built from normalized RLBot packets, which carry game seconds and full logical `last_input` action channels, among other live fields (`adapter.py:133-164`). Boxcars data cannot be truthfully inserted into schema 1 unchanged: the clock is replay-relative, action channels are incomplete, the schema has no actor-mapping/parser provenance, and exact MCT setup identity is absent. Treating a replay-derived sample as a normal MCT live capture or an eligible teaching reference would erase these differences.

This agrees with [REPLAY-01](replay-01.md): current MCT handles its own JSON attempts and match summaries but has no `.replay` importer. The existing recording tests cover the JSON import/compatibility path, not Boxcars parsing or replay actor reconstruction.

## Minimum future import contract and acceptance

1. **Explicit local selection:** Import only a file the user chooses. Keep replay file paths, display names, platform IDs, room names/password fields and raw parser output private; do not upload or share by default.
2. **Strict parse:** Pin a Boxcars release/commit and license receipt. Require a successful network-data parse, CRC/corruption handling, supported build/network version, and bounded parser resource use. Header-only or partial parses may show metadata but never a trajectory or reference.
3. **Reconstruct with provenance:** Preserve source-frame/time, `delta`, actor birth/death generations and raw recognized attribute values. Select a player explicitly and reject ambiguous/unresolved car↔PRI links. Mark computed/interpolated samples as derived and keep all missing channels null/absent.
4. **Use a separate data type:** Add replay import provenance and a replay clock in a new schema/path rather than coercing it to schema 1. Keep controller display off unless every displayed channel is explicitly present; never infer raw button actions.
5. **Fail closed for lesson matching:** Require proven map/build/mutator/body/setup and scenario identity before overlaying the trace on a lesson. If any required field cannot be resolved, allow only standalone review, not scenario comparison or an attempt reset.
6. **Keep eligibility separate:** A local replay may be a personal visualization. It is not a live MCT recording or validated teaching reference. Reference promotion would require a separately designed evidence/provenance policy, explicit permission, and independent real-game acceptance; this report supplies none.

Minimum validation should use owner-supplied replays spanning the supported build and relevant modes, but no sample file was used in this research. The first acceptance should verify: strict parse rejection on unsupported/corrupt network data; correct car/ball actor lifetimes and synchronized positions against the game's replay viewer; explicit player and body mapping; clock/delta preservation across goals, resets, actor destruction and frame gaps; no fabricated controls/events; and privacy-safe metadata display. A second acceptance would compare the reconstructed match goal times and roster against in-game replay metadata. Do not claim mechanic-event or skill-grade accuracy from that match-level check.
