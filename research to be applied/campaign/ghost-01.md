# GHOST-01 — Ghost and replay data audit

**Scope:** Read-only source and public SDK audit of ghost capture, validation, playback, rendering and persistence. No game session or runtime input was used. “Confirmed” below means source/API evidence, not in-game acceptance.

The later [boost/resource audit](boost-resource-reset-01.md) shows ordinary recordings default mutator metadata to an empty object and omit pad cooldown context. Equality of those fields is not an acknowledgement of equal resource policy or bot-pressure conditions.

## Confirmed behavior and evidence

- **No validated teaching trace is installed.** The project status and capture note say there is no bundled successful, permitted pose-and-action reference. Unit fixtures test mechanics only. The development reference-capture route writes a private candidate labelled “not validated”; its receipt says `gate: not-evaluated` and `permission.distribute: false` (`src/my_career_training/training/REFERENCE_CAPTURE.md:1-13`, `src/my_career_training/reference_capture.py:1-13,252-302`, `docs/PROJECT_STATUS.md`, `docs/NEXT_TASKS.md:43-55`).
- **Ordinary capture uses live telemetry.** The adapter reads car/ball physics and each player's game-reported `last_input`; the worker selects the human as the normal training actor and feeds observed frames to `TrainingEngine`. The official [RLBot Game Data reference](https://wiki.rlbot.org/v5/botmaking/game-data/) describes live GamePackets at 120 Hz. The recording stores per-sample car position/orientation/velocity, ball position/velocity, logical actions, game time and packet-gap markers (`src/my_career_training/adapter.py:133-159`, `src/my_career_training/game_worker.py:1111-1189`, `src/my_career_training/training/recordings.py:204-277`).
- **That is observed game input state, not a physical-button recording.** The stored channels are normalized logical actions obtained from `last_input`; the illustrative controller model uses fixed PlayStation-oriented labels, while GameWorker.draw_ghost_actions renders logical-action text. The stored binding_profile is not routed into this mapping; see [controller evidence](controller-evidence-01.md). The docs and renderer explicitly avoid claiming raw DS4 buttons or hardware capture (`src/my_career_training/training/controller.py:43-82`, `src/my_career_training/game_worker.py:1387-1403`, `src/my_career_training/training/REFERENCE_CAPTURE.md:7-20`).
- **Reference validation is structural, not independent certification.** Schema 1 requires finite increasing timestamps, oriented car poses, all logical action channels, bounded files/sample counts, explicit setup/provenance fields and game-seconds timing. Reference eligibility additionally requires actual-execution provenance, explicit distribution permission, success evidence, successful outcome, known game/framework/hitbox/map and a complete capture. The validator warns that imported success/permission claims still need real-game verification. Personal recordings are tagged local/private and cannot qualify as shared teaching references (`src/my_career_training/training/recordings.py:10-24,35-120,204-277`; `src/my_career_training/training/coach.py:77-106`).
- **Compatibility is partly exact, but scenario identity is not an explicit gate.** `compatible_recordings` compares lesson id/version, variant, game/framework versions, hitbox, map, mutators, complete `starting_state`, and time base; designated unknown values mismatch, but equal empty mutator objects are accepted. Power Shots recordings append `scenario_id`, `difficulty` (the selected lesson rank), and `scenario_version` to metadata. `practice_context` omits those three explicit keys. The full starting-state equality often distinguishes ranks/scenarios because the launch and bot roster are embedded, but an explicit identity/version comparison is missing and should be added before treating this as a durable exact-match contract (`src/my_career_training/training/recordings.py:145-172`, `src/my_career_training/training/engine.py:262-272`, `src/my_career_training/training/coach.py:348-368`, `src/my_career_training/training/scenarios.py:255-311`).
- **Two playback paths exist.** `GhostPlayback` supports watch/lead, pause/seek, ¼/½/¾/normal rate and loop. It advances from game time or the attempt clock. `GhostPractice` is normal speed, looping and user-toggled; On restarts at the first sample and anchors once to the player, Off hides pose/lines/controller immediately, retry restarts from the beginning and anchors to the intended reset car pose immediately after issuing the reset; the source does not wait for observed-reset confirmation before anchoring, and a game-clock rewind restarts playback (`src/my_career_training/training/coach.py:137-319,371-535`, `src/my_career_training/game_worker.py:630-656,833-853,1260-1265`).
- **Interpolation refuses invented movement.** Position is linear and orientation uses quaternion SLERP. There is no extrapolation outside captured samples; gaps over 0.1 s or marked packet gaps suppress the pose and coach actions. Actions are sample-held. The practice ghost is a generic fixed-dimension car wireframe; the render path calls line drawing, not actor creation or physics APIs (`src/my_career_training/training/recordings.py:293-329,407-457`, `src/my_career_training/game_worker.py:1326-1403`).
- **Ball samples are captured but never played/rendered.** `Recorder` stores ball position and velocity, but `interpolate_pose` returns only car pose/actions; both ghost snapshots call car-only `ghost_lines`. `practice_support` rejects lessons whose targets or success events depend on the ball or wall. That blocks the translated, player-anchored practice ghost for Power Shots/flip-reset style drills. The legacy best-attempt route can still show a compatible absolute car trace, but it has no ball visualization and is not a verified demonstration (`src/my_career_training/training/recordings.py:227-260,307-329,407-457`, `src/my_career_training/training/coach.py:327-368`, `src/my_career_training/bridge.py:1467-1519`).
- **The ghost does not control or collide with the learner.** Current playback produces geometry and controller-display data; `player_input_applied` is false. Rendering submits 3D lines. This supports a render-only implementation in source, but only runtime observation can confirm the visible result and absence of side effects in the live game (`src/my_career_training/training/coach.py:290-320,507-535`, `src/my_career_training/game_worker.py:1373-1403`).
- **Persistence is local and bounded in the index, with cleanup gaps.** Finished attempts with samples are written as separate UUID JSON files through the atomic writer; the save index retains 100 entries and retrieval scans the newest 30 for a lesson. Recording imports reject unsupported schema, malformed samples and over-limit files; legacy optional physics fields can remain absent. When the index is truncated, old files are not deleted, and no recording-delete action was found. Explicit selection imports a file directly; a missing or malformed indexed file can raise instead of being skipped with a clear stale-record message (`_recordings` also does not catch import errors) (`src/my_career_training/bridge.py:2053-2083,1467-1509`, `src/my_career_training/training/recordings.py:35-142`, `src/my_career_training/storage.py:10-12,145-152`).
- **Public replay wrappers are for navigating replay playback, not a demonstrated trajectory export API.** The [BakkesMod SDK](https://github.com/bakkesmodorg/BakkesModSDK) describes itself as an unofficial Rocket League SDK. Its [`GameWrapper.h`](https://github.com/bakkesmodorg/BakkesModSDK/blob/master/include/bakkesmod/wrappers/GameWrapper.h) exposes replay-state/query and replay-playback entry points; [`ReplayServerWrapper.h`](https://github.com/bakkesmodorg/BakkesModSDK/blob/master/include/bakkesmod/wrappers/ReplayServerWrapper.h) exposes replay time/FPS/current frame and seek/start playback; [`ServerWrapper.h`](https://github.com/bakkesmodorg/BakkesModSDK/blob/master/include/bakkesmod/wrappers/GameEvent/ServerWrapper.h) exposes live ball access and match replay routines. The inspected declarations do not expose a per-frame car+ball+input export. That is an observation about these public headers, not proof no private API exists. Live GamePackets remain the evidenced source for synchronized capture ([RLBot architecture](https://wiki.rlbot.org/v5/framework/architecture/)).

## Current support matrix

| Case | Source behavior | Evidence status |
|---|---|---|
| Personal attempt, car-only drill | Can be saved, selected, and shown as a personal recording; normal-speed practice is anchored ahead of the current player. | Implemented in source and unit-tested; no current gameplay claim. |
| Automatic “Your Best Attempt” | Filters for successful, untruncated, normal-speed local-player recordings and the active lesson variation. The selected item is checked against runtime context on load; a mismatch is rejected without trying the next compatible item. Legacy watch/lead displays the recorded car route. | Implemented in source; not an expert/teaching reference. |
| Explicit personal recording | Loaded after lesson/variant check plus worker compatibility validation; stays Off until the user enables practice. | Implemented in source and unit-tested. Scenario identity/version fields are not compared explicitly. |
| Ball/wall-dependent lesson | Translated practice ghost is blocked; legacy path remains car-only and has no ball ghost. | Intentional gate in `practice_support`; this does not satisfy a synchronized shot demonstration. |
| Validated teaching reference | Validator can check supplied evidence/permission shape, but availability reports `validated_demo_available: false`; no verified successful capture is installed. | Not currently available. |
| Imported old/malformed recording | Only schema 1 and bounded valid JSON are accepted; missing optional ball values may pass structural validation. Stale index/file cleanup is incomplete. | Validator exists; user-facing recovery/cleanup has gaps. |

## Recommended six-part action contract

1. **Eligibility:** Bind a demonstration to lesson id/version, explicit scenario id, selected rank/difficulty, scenario version, exact initial state, mutators, map, hitbox and game/framework versions. Keep “your recording” distinct from “validated teaching demonstration.” Require full paired car+ball samples for ball drills.
2. **Load:** Resolve only a saved recording for the active lesson/setup. Validate provenance and every sample before changing playback state. Missing, malformed, old-schema or mismatched data should fail closed with a clear message and leave the previous state untouched.
3. **On:** Start from sample zero. For ball drills, preserve the recorded car-to-ball relationship at the exact scenario start; do not translate the car independently in a way that changes the demonstration geometry. Do not reset, move or otherwise alter the learner's car, ball, bots, timer or score.
4. **Tick:** Drive car, ball and logical-input timeline from the same simulation clock and declared rate. Interpolate only within valid contiguous samples; hide all demonstration channels during gaps. Re-anchor only after a confirmed retry/reset, not on each frame.
5. **Render:** Draw translucent car and ball as visual-only geometry with synchronized logical controller state. Never create collision/score actors or send playback actions as `PlayerInput`. Preserve labels that distinguish observed logical input from physical controller presses.
6. **Off/retry/next/exit:** Off immediately hides car, ball and ghost-input display. Retry restarts the selected demonstration against the newly confirmed setup. Next rank/situation/lesson revalidates identity before any replay. Exit clears transient playback state; stale files are handled without deleting user recordings implicitly.

## Integration points and verification

- Extend `src/my_career_training/training/recordings.py` compatibility/schema only after the exact scenario identity fields and ball-sample requirements are settled.
- Extend `src/my_career_training/training/coach.py` with a ball-aware fixed-start playback model; keep the existing car-only eligibility gate until paired tracks are supported.
- Thread current scenario identity through `src/my_career_training/training/engine.py`, `src/my_career_training/game_worker.py` and the bridge’s selected-recording resolution in `src/my_career_training/bridge.py`.
- Existing relevant tests cover interpolation/gaps and provenance (`tests/test_training.py`, `tests/test_training_coach.py`), player-relative practice/Off/retry (`tests/test_training_ghost_practice.py`), worker/bridge toggles and stale acknowledgements (`tests/test_game_worker_ghost_practice.py`), and scenario reset/identity setup (`tests/test_power_shot_scenarios.py`). Add focused tests for explicit scenario/rank/version mismatches, synchronized car+ball playback, missing/stale recording-file recovery, and no gameplay mutation on On/Off/loop/retry.
- Game acceptance still needs one permitted, observed successful trace for an exact lesson/rank/scenario version; start-state and full capture validation; side-by-side visual alignment of car, ball, target and logical controller at normal speed; forced gap/timeout/retry/next/exit checks; and confirmation that ghost rendering never affects the live attempt, collisions, goals or scores. No such runtime proof is claimed here.
