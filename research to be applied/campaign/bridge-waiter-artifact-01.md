## Wait behavior in the pinned build-input DLL

REA managed-member inspection was complete for the selected `Bridge.TCP.MessageReader`, `Bridge.TCP.TcpMessenger`, and generated state-machine types (`ev_f22a85b184917d2f453be7d487b05ed4206644c9ee08e528d41f0904bf1856c7`, with exact `MessageBuffer` and `ReadStreamAsync` state-machine follow-ups `ev_3c791f3a2ebab9b2b38f54498e989e1fe5d845ff47b77fa9addd82d7acdd0098`, `ev_8901199ff487e1d608a70aa3a66b7db054730b48f21308d0c2a350082613aa89`). Tokens below are build-local to the DLL hash and MVID above.

1. `TcpMessenger.WaitForAnyMessageAsync` (`0x060005fd`) obtains its `TcpClient` stream and delegates to `MessageReader.WaitForAnyMessageAsync` (`0x060005f9`).
2. The reader's async state machine (`<WaitForAnyMessageAsync>d__1.MoveNext`, `0x0600077e`, CIL SHA-256 `04abf060a321b2b1d7c8cfd23aad1a82237c51ec489868c6829a77d736b3a130`) creates a new `MessageBuffer`, calls `MessageBuffer.ReadStreamAsync` once, awaits it, and forwards the resulting Boolean. This path does not call `ReadMessage` or return a payload buffer.
3. `MessageBuffer.ReadStreamAsync` (`0x0600076c`) awaits one `System.IO.Stream.ReadAsync` in `<ReadStreamAsync>d__3.MoveNext` (`0x060007be`). Its continuation returns `true` when the read count is positive and `false` when it is zero. Microsoft's [`Stream.ReadAsync` contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.stream.readasync) says the operation advances the stream by bytes read and may return zero at end-of-stream. The helper therefore detects a positive stream read, not a complete length-prefixed message. Its temporary `MessageBuffer` is not returned or retained by the waiter; any interaction with a later receive loop needs runtime or caller-path evidence.
4. The same state machine has a nested exception region with catch token `0x0100000f` (REA labels it `System.Object`, with `class_type_identity_resolved:false`); its handler stores `false`. An outer region with catch token `0x0100002f` (REA label `System.Exception`, likewise unresolved) stores the exception and faults the task. The selected CIL decodes both handlers and their control flow; the unresolved catch-type identity and lack of deployed-runtime observations limit which exception is actually observed there.

The separate `MessageReader.ReadAllAsync` path (`0x060005f8`) uses another async iterator and calls `MessageBuffer.ReadMessage`. That distinction reinforces that `WaitForAnyMessageAsync` is a byte-arrival predicate, not the frame parser. It does not resolve whether the staged EXE uses this implementation or how its callers sequence reads. No dynamic test was run.

## Sender behavior in the same DLL

`TcpMessenger.Send` (`0x06000601`) reads `_byteSentThisTick` (field `0x04000142`, `int32`). Its CIL first accepts `ArraySegment.Count <= 65,535`; a larger count logs “Message too long to send” and returns. It then compares the count with `65,535 - _byteSentThisTick`; an over-budget message logs “Too many bytes sent this tick, skipping message” and returns. On the accepted path it adds the payload count to `_byteSentThisTick`, converts the checked count to `uint16`, and calls `WriteMessageLength` (`0x060005ff`). The length prefix is written separately and is excluded from `_byteSentThisTick`. Thus, between explicit resets, the per-instance counter admits up to 65,535 payload bytes in aggregate. The literal log message says “this tick,” but this code alone does not establish that reset windows match game ticks. `ResetByteCount` (`0x06000600`) explicitly stores zero in the counter. The constructor (`0x060005fa`) does not assign it, and the complete `TcpMessenger` method inventory has no `.cctor`; reset cadence and messenger sharing are caller behavior, not established by this Bridge type alone.

After the checks, `Send` invokes synchronous `Stream.Write` for the two-byte length prefix and payload when its client field is non-null; the CIL skips those writes for a null client. There is no local exception region; this establishes neither actual blocking duration nor what its caller does with a write exception. The Microsoft [`Stream.Write` documentation](https://learn.microsoft.com/en-us/dotnet/api/system.io.stream.write) identifies this as the synchronous counterpart to `WriteAsync`.

## Batch rejection and clear-progress boundary

`TcpMessenger.Send` is `void`. Its oversized and over-budget branches log and return normally at CIL offsets 14–24 and 48–58; they provide no success value or retry signal. `RenderingCommandQueue.Send` (`0x06000765`) passes that method as the flush callback. In `CommandQueue.Flush` (`0x06000750`), the callback invocation at offset 157 is followed unconditionally on normal return by `Reset` (`0x06000751`) at offset 163. `Reset` clears the FlatBuffer builder and queued-message list. Thus, in the pinned build-input CIL, a size/budget rejection that returns normally is followed by clearing that serialized local batch, without a success receipt or retry in these selected methods. If the callback instead throws during a write, `Flush` has no local exception handler and its reset call is not reached.

In pinned Core source, `Rendering.SendRenderClears` at `Rendering.cs:244` dequeues IDs and queues remove commands before calling the void `RenderingCommandQueue.Send` at line 253, then returns whether `_renderClearQueue.Count == 0` at line 255. That Boolean reports local ID-queue backlog only; it does not report whether `TcpMessenger.Send` accepted or the peer processed the payload. These are static conditional consequences of the pinned source/build-input pair, not evidence that a deployed server actually rejected a batch, lost a render command, or hung.
