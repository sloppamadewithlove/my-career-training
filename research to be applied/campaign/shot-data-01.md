# SHOT-DATA-01 — BakkesMod shot JSON as MCT scenario input

## Scope and result

Read-only inspection of `BakkesMod2-Plugins` at pinned commit `f412cd66ce0735be4aeb21ca41325337eb959aa0`, focused on `TrainingPlugin/JsonShot.*`, `TrainingPlugin.cpp`, and `WorkshopPlugin.cpp`, compared with frozen MCT Power Shots (`work/reviewed-training`). This is not the native Rocket League custom-training-pack format and does not run or download a shot.

The format can provide **partial initial physics** for an offline exercise: a ball state (`location`, `velocity`, `rotation`, and JSON `torque`) and some car poses. It does not define a complete MCT lesson, success rule, timeout, rank, actor roles, map/mutators, or a validated target. A strict import therefore needs MCT-owned metadata and validation; a legacy file cannot become a Power Shots scenario losslessly by itself.

The pinned Git tree contains no `.json` fixtures and no tracked `LICENSE`, `COPYING`, or `NOTICE` file (`git ls-tree -r --name-only` at the pin). The parser references external `utils/parser.h`, which is not tracked in this plugin tree, and the replay snapshot references an absent `bakkesmod/data/replay_template.json`. Thus there are no small shipped JSON examples or complete template to validate. Repository provenance is the pinned GitHub source; license or redistribution rights are not established by this file pass.

## Observed shot shape and behavior

`JsonShot.h:49–99` declares `ball`, `player`, `start`, `dest`, `options`, `speed`, and `json_shot`:

| JSON key / shape | Parser and caller behavior | MCT mapping limits |
|---|---|---|
| `start.ball`: object or array of objects with `location`, `velocity`, `rotation`, `torque` | `JsonShot.cpp:39–53, 106–116`; parsed ball state uses `VectorString` / `RotatorString`; `torque` is stored as `angvel`. `set()` randomly chooses one start ball (`:170–192`). | A single fully specified ball can map to the MCT ball's position, velocity, rotation, and angular velocity after unit/axis conversion. Multiple starts are randomized, not identified as a stable scenario variant. |
| `start.player`: object or array; fields `index`, `location`, `velocity`, `rotation` | `JsonShot.cpp:56–72, 117–129`; `index` defaults to 0. A single object is always stored under map key 0; the array branch was intended to store by parsed index, but parses `player` (the whole array) instead of `element` (`:119–123`), so array parsing is not reliable. `shot_reset` applies selected car states by server car-array index (`TrainingPlugin.cpp:156–166`). | No team/role/stable actor identity, boost, car angular velocity, jump flags, or player name. One player can only be assigned to MCT's Human explicitly; index alone must not map to a keeper/defender. Partial car state is not a lossless MCT reset. |
| `end`: object or array of `{x,y,z}` destinations | `JsonShot.cpp:133–141`; when `usevelocity` is false, a random destination and a speed from `speed.min/max` feed `ServerWrapper::GenerateShot` (`:153–167, 194–205`). `select_randomly` uses a uniform integer selection over a nonempty range (`JsonShot.h:124–136`); the external float `random()` helper and its endpoint/distribution semantics are not in this tree. | These are launch destinations, not goal rectangles, scoring rules, or success events. They cannot be used as an MCT goal target without separately authored geometry and outcome logic. |
| `speed`: `min`, `max` | Parsed without visible presence/range validation (`JsonShot.cpp:144–148`); `speed` members have no initializers (`JsonShot.h:85–88`). Used only for generated velocity when `usevelocity` is false. | Not a timer or difficulty/rank. Missing, non-finite, inverted, or extreme values need strict rejection; exact random speed selection is unverified because the helper is absent. |
| `options`: `shootongoal`, `usevelocity`, `shootonground`, `script` | `JsonShot::init()` parses those four options (`JsonShot.cpp:79–103`); it does **not** parse `disablemirror`. Exact velocity is used for `usevelocity=true`; otherwise velocity is generated. `shootonground` zeroes generated Z velocity only. `shootongoal` is 0/1/2 (false/blue/orange) and tries to derive a Freeplay destination, but the code writes `vs.x` for the Z range, pushes directly to `shot.end` rather than `currentshot.end`, then overwrites `shot` with `currentshot` at line 150. Thus the derived destination is not retained; additionally `vs.x` is assigned twice and `vs.z` is never assigned (`:79–96, 150`). `JsonShot::set()` reads `shot.options.disablemirror` when choosing the mirror CVar (`:170–177`), but loading JSON does not populate that member; a JSON `disablemirror` field therefore has no effect through this parser path. `script` is executed through `executeCommand` during reset (`TrainingPlugin.cpp:168–169`). | `shootongoal` does not provide a usable destination or authoritative success meaning in this path; do not execute `script` during import. Ambient CVar behavior can affect the result: `shot_randomization` is added to velocity components in `get_shot_data_from_console` (`TrainingPlugin.cpp:12–24, 132`). |

Other parser details (`JsonShot.cpp:13–37`): missing/null vector or rotation components become string zero; numeric JSON values are converted via `std::to_string(float)`; strings pass through. There is no schema version, finite-number/range check, required-field validation, or explicit report for unknown keys in the inspected path. The constructor falls back to `./bakkesmod/data/emptyshot.json` if its candidate paths do not exist (`JsonShot.cpp:226–250`). `json_shot.name` is declared but not populated by `init()`.

## Units, randomization, mirroring, and reset sequence

Vectors flow to BakkesMod `Vector` setters / `GenerateShot` without an application-level unit conversion. The parser helper implementation is absent, so accepted textual syntax and validation are unverified. Rotations flow through BakkesMod `Rotator`; the MCT-pinned SDK declares `Rotator` as integer Pitch/Yaw/Roll in Unreal rotation units, with conversion constants (`WrapperStructs.h:12–17, 222–231`). MCT's RLBot scenario state uses radians (see [PHYSICS-01](physics-01.md)). An importer must convert rotation and preserve axis order; copying the integers directly into MCT's float radians is wrong. The exact public TrainingPlugin build SDK revision is not pinned by its project files, so confirm against the targeted header/runtime before relying on that conversion.

The active TrainingPlugin torque path also does not preserve JSON vector order: `JsonShot::set()` writes `torque.x/y/z` into the pitch/yaw/roll CVars respectively (`JsonShot.cpp:185–187`), while `shot_data::get_ball_start_angvel()` reconstructs a vector as pitch/roll/yaw (`TrainingPlugin.h:43–45`), which swaps the JSON Y/Z components before `SetAngularVelocity` (`TrainingPlugin.cpp:197`). Read the JSON field directly in a new importer and validate its axis/unit mapping; do not copy this legacy CVar permutation by accident.

Mirroring is not a safe reusable contract as implemented. `TrainingPlugin::mirror_it(Vector)` negates X for all vector values; the `Rotator` overload reflects yaw using constants near 16383 (`TrainingPlugin.cpp:64–94`). `JsonShot::set()` randomly chooses the mirror CVar unless `shot.options.disablemirror` is true (`JsonShot.cpp:170–177`), but `JsonShot::init()` never parses a JSON `disablemirror` option (`:79–103`), so a file field cannot disable that randomization through this load path. Reset applies these functions to player/ball pose and velocity, and to ball angular velocity/rotation (`TrainingPlugin.cpp:146–165, 192–198`). MCT uses a separately authored reflection for positions, velocities, angular velocity as an axial vector, and yaw/roll (`training/scenarios.py:169–205`). An importer must resolve a concrete variant itself; do not claim exact MCT parity.

`shot_load` parses a named JSON; `shot_generate` fills CVar start state; `shot_reset` stops and relocates the ball, applies configured car poses, runs the `script`, then after `shot_waitbeforeshot` (default 0.2 s) applies ball velocity, angular velocity, and rotation (`TrainingPlugin.cpp:101–135, 137–211, 213–225`; `JsonShot.cpp:170–220`). `shot_countdowntime` is registered as 1 s but its only visible use is in a commented-out Tutorial path (`TrainingPlugin.cpp:134, 202–211`); it is not a shot-file timeout. The active reset/generate notifiers require in-game, loaded shot, and reject Custom Training (`TrainingPlugin.cpp:137–142, 221–225`), despite the plugin's broader Freeplay/Custom Training declaration (`:10`).

## Workshop versus native packs

The deprecated Workshop path is an ID/cache/RCON flow, not a pack-file importer. `WorkshopPlugin::workshop_shot_load` looks for `bakkesmod/shots/cache/<id>.json`; if present it dispatches `shot_load`, `shot_generate`, and `shot_reset`, otherwise requests the shot remotely and writes the returned JSON into that cache (`WorkshopPlugin.cpp:104–149`). Playlist responses are comma-separated shot IDs, stored as an ordered/random list; `workshop_playlist_next` selects an ID and loads it (`:29–42, 122–134, 171–185`). The source comments label these commands deprecated. The response data shape is not a local native training-pack code or Rocket League pack file.

`createReplaySnapshot()` samples the replay ball and camera/view-target actor pose/velocity/rotation plus ball angular velocity, then fills a missing external template (`WorkshopPlugin.cpp:45–90`). That shows which physics values the replay snapshot intended to capture, but not the full JSON envelope, because its template is absent. It contains no attempt clock, rank, player role/team, outcome gate, or lesson metadata.

## Comparison with MCT and import boundary

MCT Power Shots authors 12 stable scenario IDs and eight intended pressure profiles (`training/scenarios.py:13–44, 294–363`). Each definition contains explicit ball and Human state, optional bot states/roles/teams, separate `starting_state` and `settle_state`, launch/receiver/target geometry, rank-derived timeout, and provenance (`:247–363`). The engine evaluates launch → fresh Human touch → target crossing → authoritative team score, or times out (`training/engine.py:477–579, 815–835`). The Soccar adapter sets the complete ball and car roster through RLBot state setting (`adapter.py:112–119, 167–203`). None of those MCT outcome/pressure/roster rules are encoded by `JsonShot`.

**Representable subset:** numeric one-ball launch physics, plus an optional partial player pose, can seed a separate MCT-owned one-shot template if rotations are converted and missing car fields have an explicit policy. For an exact start-state transfer, require an explicit ball location/velocity/rotation/angular-velocity and explicitly mapped Human pose; `torque`→angular-velocity requires validated axis/unit parity. Because the file lacks boost and car angular velocity and does not say whether player index 0 is the Human, complete MCT actor state is not lossless. Multiple ball/destination choices and random mirroring/speed also require resolving and recording the chosen variant.

**Not represented:** MCT settle state, bot roster/roles/teams and controller profile, map/mutators, rank/time limit, instructional text, target rectangle, success/timeout evidence, reset/attempt identity, source/license metadata, or versioned schema. A future importer must either keep these files as “launch-state only” templates with separate MCT-authored metadata, or reject them as full Power Shots scenarios.

## Minimal future import validation

1. Select a local file through a bounded read-only importer; do not use legacy command/path resolution, Workshop RCON, package download, or `options.script` execution.
2. Require a JSON object and a recognized explicit version/profile; reject unknown schema versions, oversized files, missing required vectors, empty start/end arrays when generation needs them, non-number/non-finite values, out-of-range coordinates/speeds, and invalid `min > max`.
3. Support a deterministic mode only: one ball with explicit velocity, one explicitly assigned Human pose, no random source/destination/mirror and no script. Record `source_format=bakkes-json-shot`, source hash, and every conversion/assumption. Keep unresolved multi-player, bot, and multiple-ball files unsupported.
4. Convert Unreal `Rotator` values to MCT radians using a version-verified map; treat `torque` as candidate angular velocity only after axis/units validation. Use MCT's own explicit mirror transform if a mirrored variant is requested.
5. Author MCT-only settle state, training timeout, target and success semantics separately. In isolated offline acceptance compare imported ball/car state against the source values, verify timer/reset/outcome behavior, mirror result, and retry repeatability; never infer a complete drill from `end` or `shootongoal` alone.
