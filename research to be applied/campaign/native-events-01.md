# Native training event trace: public-source findings

Date: 2026-10-27
Scope: public BakkesMod source and SDK declarations only. No game process, runtime event, or stock Psyonix source was accessed.

## Finding

Within the inspected default-plugin source files, the exact BakkesMod hook strings confirmed here cover Tutorial and TrainingEditor entry/exit. This bounded finding is not an exhaustive search of all public BakkesMod plugins. The SDK also exposes tutorial, training-UI, and ball wrapper methods. The sources do **not** reveal the stock shot-timeout caller, its timer start condition, or a causal link from timeout to ball fade, hide, reset, or destruction. The method names below are observation leads, not recovered game implementation.

The `TrainingPlugin` in the BakkesMod repository is a shot-control example, not Rocket League native training. At the pinned repository commit, the `shot_reset` and `shot_generate` handlers register their own console notifiers and return when `IsInCustomTraining()` is true. It therefore cannot establish stock-training lifecycle behavior.

## Exact hook names: confirmed versus candidates

Within the checked-out pinned `BakkesMod2-Plugins` source files, the four strings in the table were the only ones confirmed by this bounded inspection. This does not establish that other public plugins lack additional lifecycle hooks. Other method strings can be proposed using the demonstrated `Function TAGame.<class>.<method>` convention, but remain candidates until a runtime trace confirms invocation and class spelling. Examples from the Tutorial wrapper are `StartTimers`, `StartRound`, `StartNewRound`, `OnPlayerRestarted`, `HandlePlayerResetTraining`, `RedoRound2`, `CommitRedoRound`, `ResetRoundTime`, `ResetBalls`, and `SetDifficulty2`. Do not call these proven timeout or completion hooks. For the ball fade methods, first confirm the runtime class/function event path; the public wrapper header alone does not supply a hook string or callsite.

## Smallest useful lifecycle trace

A future owned-game, read-only trace should capture one stock Aerial/Striker drill (and a tutorial separately if needed):

1. Mark `GfxDataTraining` start request/type/difficulty, then mark `GameEvent_Tutorial_TA.OnInit`; keep editor `StartPlayTest` out of the stock trace.
2. During setup and the attempt, timestamp round/progress/difficulty/tip, `GetGameTimeRemaining`, `GetGameStateTimeRemaining`, ball identity/presence/location, and the ball fade-in/fade-out/end-hidden flags plus actor hidden state. The UI timer must be recorded separately if visible, since neither clock is documented as its source.
3. In parallel, observe candidate Tutorial callbacks `StartTimers`, `StartRound`, `StartNewRound`, `OnPlayerRestarted`, `HandlePlayerResetTraining`, `RedoRound2`, `CommitRedoRound`, `ResetRoundTime`, and `ResetBalls`. Record entry/exit timestamps and caller context where the runtime hook API permits.
4. Continue sampling through the displayed timer reaching zero and through a user retry. Compare both clocks, callback sequence, ball pointer/presence, and visibility flags. Same ball still present with fade/hidden flags changing is evidence of visual hiding; actor disappearance/replacement is evidence of removal/reset. A timer transition alone is not evidence of ball causality.
5. To claim the responsible writer, separately observe the validated runtime calls to fade/hide/destroy/reset operations in this same interval. If those calls are not exposed as hookable functions, this trace can establish correlation only; a supported runtime probe or game implementation source is still required.

This plan distinguishes a timer reaching zero from a ball becoming visually hidden or being removed, while keeping all mutation APIs out of the observer. It does not promise that the candidate callbacks are hookable in every current game build.
