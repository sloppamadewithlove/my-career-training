## What the pinned DefenderPlugin does

The source name is misleading if interpreted as an AI goalkeeper. It declares `PLUGINTYPE_FREEPLAY` (cpp:7), registers `defender_active` (default `0`), `defender_shotspeed` (default string `"(800, 1100)"`), `defender_cooldown` (`"(3000, 6000)"`), and `defender_difficulty` (`"8"`) (cpp:10–16). The difficulty default string is `8` despite declared bounds 0..1 (cpp:14); the host's actual clamping/default behavior is not established here, so do not translate that literal into an MCT difficulty level. The tuple-like defaults are passed through `getFloatValue()`; this trace does not establish how BakkesMod parses them. `defender_start` sets active to 1 and is declared Freeplay-only; `defender_stop` sets it to 0 (cpp:25–32). The single-shot notifier is commented out (cpp:18–22).

While active, `CheckForShot()` polls every 100 ms and turns the feature off when `IsInFreeplay()` is false (cpp:50–67). `HandleShot()` waits on a server-seconds cooldown and whether the ball is already moving toward `destinationGoal` (header:21; cpp:80–89). It requires at least one goal, but derives the aim point from fixed coordinates `(0, -5120, 0)` plus an offset, and uses goal index 0 only for the count check; the retrieved `GoalWrapper` is unused (cpp:94–107). It reads the game car but does nothing with it (cpp:108–112). It calls `GenerateShot`, then stops the ball and sets its velocity (cpp:114–118). This is a scripted shooter that supplies goalkeeper-save attempts, not a bot goalkeeper or user-controllable defender.

The plugin also hooks `Function GameEvent_Tutorial_TA.Active.HandleHitGoal` during load. When active, that handler stops and relocates the ball (cpp:34, 123–133). Its `EventHitBall` post-hook records server time and schedules a new cooldown but does not identify which car touched the ball (cpp:135–140, 152–160). `onUnload()` sets `defender_active 0`; the false branch unhooks `EventHitBall`, but source has no restoration of the previous `sv_freeplay_enablegoal` value set to `0` at activation (cpp:37–40, 143–160). It also does not explicitly unregister the `HandleHitGoal` hook in `onUnload`; host/framework cleanup behavior is not established here. These are source facts, not tested host behavior.

## What MCT means by keeper and defender

MCT’s Power Shots scenario builder creates a team-1 keeper from Gold upward; Diamond and higher also create a team-1 defender. Bronze and Silver have neither. These are authored pressure profiles, explicitly labeled “Intended difficulty only; not a certified bot rank” (`training/scenarios.py`:29–43, 247–291, 320–350). The role descriptors are named “Scenario Keeper” and “Scenario Defender” (`:366–374`), and `scenario_actor_controllers()` maps each role to its own controller (`:393–401`). The keeper controller delays, delegates decisions to `SpecialistController("keeper", ...)`, and applies a goal-boundary guard (`:404–474`); the defender similarly delays and delegates to `SpecialistController("defender", ...)` (`:477–522`). `game_worker.py` builds those per-index controllers and sends their `PlayerInput` at up to 120 Hz, neutralizing scenario bots outside the active attempt (`:536–547`, `:1271–1292`). `adapter.py` represents the bots as custom-bot player configurations, appends the human player last, and requests Soccar with state setting for lessons; in that config `freeplay` is `training and capture is not None` (`:77–119`).

These controllers actively drive bot cars. DefenderPlugin only changes ball velocity/location. Its `IsInFreeplay()` gate is an explicit context requirement; MCT lessons request a Soccar offline match with `freeplay=false`. The exact BakkesMod meaning of that predicate in a session created through MCT is not proven without runtime evidence. Compatibility should therefore be marked unavailable/unknown until a safe, owned-session probe confirms the gate and event contexts; the plugin must not be assumed to work merely because the plugin type says Freeplay.

MCT’s existing Power Shots success chain checks for the human’s fresh touch, the configured goal crossing, and an authoritative team-0 score. It also tracks keeper contact and rejects a later keeper touch (`training/engine.py`:478–579, 1233–1246). In the inspected source, the actor list for this chain contains the human and keeper only (`:507–510`), even when a defender role is present. Thus this engine path does not establish whether a defender touch invalidates success. A keeper-training mode or any lesson using an active defender needs an explicit, separately tested attribution policy; do not report save/shot quality based on the current chain if untracked defender contact can intervene.

## Integration requirements and limits

Treat the plugin as an optional ball-shot generator, never as a replacement for MCT’s keeper/defender controllers. Before offering it in an owned MCT session, an adapter would need to:

1. Check `IsInFreeplay()`/event availability in the exact owned session and fail closed if unsupported; expose requested vs. applied state and read back `defender_active`.
2. Snapshot `sv_freeplay_enablegoal` and restore the prior value on disable, cancellation, partial activation failure, session return, and unload. The pinned plugin itself does not do this.
3. Define and verify which goal the user guards. The plugin hard-codes a negative-Y aim coordinate and does not use the retrieved goal object’s location; MCT Power Shots targets the positive-Y plane (`training/engine.py`:1137–1162). These paths are not directly interchangeable.
4. Attribute each injected shot and ball relocation to the plugin, and exclude those changes from user contact, save, score, or success evidence. The plugin’s hit hook does not filter by actor, and its goal hook relocates the ball.
5. Disable idempotently, stop future polling, restore cvars and owned state, and prove hook cleanup. The source shows `EventHitBall` unhooking on inactive but leaves goal-hook unload semantics unresolved.
6. For a true MCT goalkeeper drill, spawn/drive the user’s opponent shooter as an owned bot/controller with a controlled ball launch. For an active defender, preserve its actor index/team and include its touches in the outcome chain. Do not map the plugin’s name to MCT’s `Scenario Defender` role.

**Untested:** installed DLL identity/version, host parser semantics for tuple-like cvar defaults, behavior of the `Tutorial_TA` event hook in MCT Soccar, whether the plugin’s freeplay predicate is ever true in MCT lessons, coordinate-to-goal orientation in the live game, cooldown dynamics, and reliable cleanup on unload. Static declarations and source calls do not prove successful runtime compatibility.
