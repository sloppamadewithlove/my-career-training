# REPLAY-01 — replay-backed review and training entry points

Research-only source pass, 2026-10-27. No game, input, process attachment, compile, or tests were run. This report is limited to the current `work/reviewed-training` source and the BakkesMod SDK headers fetched by its CMake pin. Header declarations are not evidence of runtime behavior.

## Findings

The product currently handles two things called “replay,” neither of which imports Rocket League `.replay` files:

1. **Attempt recordings** are the product's own versioned JSON telemetry. The lesson engine starts a `Recorder` from observed training frames; the UI offers “Replay your best attempt”; the bridge imports `*.json` and routes a validated JSON object to `GhostPlayback` / `GhostPractice`. The current coach playback interpolates the car path, holds logical actions, and hides across packet gaps. It does not sample or drive the Rocket League replay viewer. See `src/my_career_training/training/recordings.py:10-11,35-168,204-279,307-325`, `src/my_career_training/training/engine.py:778-805`, `src/my_career_training/ui/Main.qml:462`, `src/my_career_training/bridge.py:1500-1556`, and `src/my_career_training/game_worker.py:1034-1075`.
2. **Match review** is a bounded summary of current observed match telemetry. `GameWorker` updates `MatchReview` on the live normalized packet path and includes its timestamped notes in the completed-match result; the bridge bounds and persists that summary with the fixture. It does not read replay files or extract a replay timeline. The review explicitly distinguishes scoreboard changes from causes and uses labeled coaching heuristics; its module states that it produces no skill rating or outcome attribution. See `src/my_career_training/game_worker.py:1327-1335`, `src/my_career_training/review.py:1-5,78-97,124-212`, and `src/my_career_training/bridge.py:2128-2140`.

The repository source search found no `.replay` file parser/importer, replay playback call, or replay trajectory export. No `.replay` fixture was present under the project tree. In the native plugin, `IsInReplay()` appears as a context/safety flag; replay is excluded from lesson input, ghost input, and launch/session paths (`plugin/src/MyCareerTraining.cpp:302,852-862,1136-1137`; `plugin/include/TrainingLessonInput.h:156`; `plugin/include/TrainingGhostInput.h:151`). These guards are not replay integration.

## SDK surfaces: declared, not consumed

The plugin's `CMakeLists.txt:26-30` fetches BakkesModSDK commit `479e8f571cf554b25f4eeb64d611dec4133edcaf` with a fixed archive SHA-256. The following are declarations in that pinned source, not calls made by this product:

- `ReplayManagerWrapper` can load headers from the demo folder, return loaded replay records, report header-loading state, and start a replay from an object, absolute file path, or replay ID with optional map/time (`ReplayManagerWrapper.h:13-40`). `ReplayWrapper` declares `ImportReplay` / `ExportReplay`, replay metadata, frame count/current frame/record FPS/current time/accumulated delta and skip targets, `SkipToFrame/Time`, `StartPlaybackAtFrame/TimeSeconds`, stop/start record/playback, and playback/time-skip events (`GameEvent/ReplayWrapper.h:21-114`). `GameWrapper` exposes `IsInReplay`, `GetGameEventAsReplay`, `GetReplayManagerWrapper`, `PlayReplay`, and `PlayReplayFromTime` (`GameWrapper.h:54,71,84,159-160`).
- `ReplayServerWrapper` exposes replay object, elapsed time, FPS, current frame, keyframes, skip, and playback-at-time/frame controls (`ReplayServerWrapper.h:11-22`). `ReplaySoccarWrapper` exposes goal/highlight lists and per-player aggregate stats (`GameEvent/ReplaySoccarWrapper.h:12-28`). Its public structs include goal frame/name/team and replay player name, platform, online ID, team, score, goals, assists, saves, shots, and bot flag (`core/replay_structs.h:7-48`). Those stats are match summary fields, not a frame-by-frame skill or rank measure.
- The SDK also declares a replay-viewer UI surface: `ReplayViewerDataWrapper` exposes current frame, available camera-mode metadata, focus actor, pause-for-scrub, slomo, FOV, `AdvanceTime` / `AdvanceToFrame`, and mode/focus setters (`ReplayViewerDataWrapper.h:17-42`). `CameraWrapper` has generic camera state, focus actor, camera transform, and fly-cam/ball-target methods; `BaseCameraWrapper` has free-cam distance/offset getters and setters (`GameObject/CameraWrapper.h:17-34`; `GameObject/BaseCameraWrapper.h:62-69`). No runtime mode list or safe-call behavior was tested. These declarations suggest viewer controls, not an automatic camera-freeze or trajectory-export facility.
- A plausible *sampling* route is to select/load a replay, observe its playback timeline, and sample world actors while it advances. The pinned declarations connect `ReplayServerWrapper` to `ServerWrapper`; server/team/PRI/car wrappers expose game ball(s), teams/members, cars, and actor location/velocity/rotation/angular velocity (`GameEvent/ServerWrapper.h:99`; `GameEvent/TeamGameEventWrapper.h:17`; `GameObject/TeamWrapper.h:32`; `GameObject/PriWrapper.h:74`; `Engine/ActorWrapper.h:14-23`). `VehicleWrapper` has a boost component whose wrapper exposes replicated boost amount (`GameObject/VehicleWrapper.h:65`; `GameObject/CarComponent/BoostWrapper.h:43`). This is an inference from wrapper composition, not a proven replay telemetry contract. There is no declared SDK method here that returns the complete decoded state of every replay frame as a standalone array or direct binary parser API.

## What a replay can seed, and what is missing

The current normalized RLBot packet records full observed physics for each sampled car and the ball: position, velocity, rotation, angular velocity; cars also have team/index, boost and last logical actions. It includes game time/frame, game speed, latest-touch data, boost-pad activity, and optional ball prediction (`src/my_career_training/adapter.py:127-165`). The current training state writer accepts a single ball and the human plus optional selected bots, with position/velocity/rotation/angular velocity and car boost (`adapter.py:167-205`). That makes a **selected snapshot** a plausible seed for a compatible training setup, subject to a real adapter and full-state validation.

The custom attempt recording is deliberately narrower than the live packet. Each sample persists elapsed `game_seconds`, the selected car's position/rotation/velocity/actions, ball position/velocity, gap marker and game speed, with optional **car** angular velocity, wheel contact, and boost (`recordings.py:204-279`). It drops subsequent ball rotation/angular velocity, other-player trajectories, boost-pad state, and per-sample full roster/team mapping. `observed_start` keeps a one-time copied car/ball frame, while `metadata.starting_state` is the configured lesson state, not a guarantee that the attempt began at precisely that observed state. Therefore the existing JSON is not a faithful full-match trace.

For a new replay adapter, the least speculative first output is a **private, annotated replay segment** (timestamps, observed actor/ball tracks, touch/goal/highlight markers) with explicit data gaps. A later, player-confirmed action could derive a candidate lesson snapshot. Do not auto-convert a match clip into a validated teaching reference or reset the user into it: replay worlds may differ in map, mutators, game build, hitbox, team orientation, player index, or actor roster, while the state writer covers only a bounded actor set and one ball. Existing recording compatibility already rejects unknown/different lesson/setup context (`recordings.py:145-168`); replay metadata should add replay/build identity and a reviewed setup fingerprint before any cross-session application.

**Coordinate/team transform:** current frames retain the game-world basis. The lesson's Power Shots mirror explicitly transforms every car/ball/bot position and velocity, axial angular velocity, and rotation, plus goal lane/target coordinates (`training/scenarios.py:169-204`); the scenario also assigns the human to team 0 and defenders to team 1 (`scenarios.py:344-363`). A replay importer must identify the player car by stable roster mapping, preserve the source-side coordinates or apply a complete transform to every actor and target, and remap teams/goal direction consistently. Reflecting only the human car or swapping team labels is insufficient. The existing `MatchReview` convention says team 0 defends negative Y (`review.py:78-80`), but no replay-side-to-training-side runtime mapping is proven.

**Clock:** the SDK provides replay frame, record FPS, current time, elapsed time, accumulated delta, and skip callbacks. The manager comment recommends using current frame divided by record FPS for an accurate start time (`ReplayManagerWrapper.h:18-40`). The lesson recorder instead starts a relative clock at its first packet and requires monotonic `game_seconds`; the coach avoids extrapolating or interpolating across gaps (`recordings.py:227-260,307-325`). Replay playback can seek and change slomo (`ReplayViewerDataWrapper.h:17-42`), so frame/FPS, elapsed playback time, and RLBot game seconds must not be treated as identical without calibration. Store original frame as the primary stable key, map to a monotonic segment offset, and mark seek, pause, slomo, missing-frame, and actor-discontinuity boundaries. Never interpolate through an unobserved jump.

## Existing tests and evidence gaps

Relevant existing source tests cover only the product's custom data: `tests/test_training.py:330-374` checks JSON import rejection/private provenance, boost optionality, compatibility, and pose gap handling; `tests/test_training_coach.py:40-130,157-173` checks custom ghost timing/actions and imported-reference caveats; `tests/test_training_ghost_practice.py:177-260` checks gaps and non-mutating ghost snapshots; `tests/test_review.py` covers bounded telemetry review. `tests/test_power_shot_scenarios.py:625` ensures a goal replay/cadence gap cannot resume or credit a goal. These do not prove a `.replay` importer, replay viewer navigation, or frame extraction. They were inspected, not run.

Before implementation, resolve: (1) which `ReplayManager` / viewer wrappers and playback callback schedule are available on the declared host build; (2) reliable per-frame player/car identity and team/side mapping through the entire replay; (3) sampling cadence, frame/time agreement and behavior across seek/slomo; (4) which mutators, boost-pad states, hitbox/map/field variants and game versions can be recovered/compared; (5) whether a replay-derived state can be safely written into the existing RLBot lesson flow after replay exit and verified against observed state; (6) local privacy boundaries for player names, platform IDs, raw replay paths and any future sharing. The SDK's `GetFilePath`, replay ID/name/date/player-name metadata and `ReplayPlayerStats.online_id` make raw replays and derived records privacy-sensitive. Keep processing local by default, redact identity/path fields from summaries, and do not upload raw replays without separate, explicit user permission.

No match skill-rating or competitive-rank claim follows from replay score/stats or heuristic moments. The next safe adapter candidate is user-selected local replay discovery + metadata/goal/highlight index + stock viewer launch/seek, then an explicitly labeled read-only segment sampler. Snapshot-to-lesson should remain a later, separately validated opt-in.
