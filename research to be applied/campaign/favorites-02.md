# FAVORITES-02 — identity, stale-item recovery, and visible row behavior

Source-only follow-up to `work/browser-identity-research.txt`, 2026-10-27. This describes current source contracts, not in-game acceptance. No code was changed and no tests were run; the main agent already ran a five-test favorite selection, so I did not repeat it.

## Persistence and resolver path

The unified browser stores `browser_favorites` as ordered records with exactly `{type, id, title, subtitle, detail}`. `storage.py:24-29,42-61` limits the list to 512, makes `(type,id)` unique, validates a bounded namespaced ID and sanitized display snapshots, and rejects extra fields. Favorite records deliberately have no action, source URL, version, rank, scenario, lesson variant, path, or package payload. Thus a saved title helps identify an unavailable item, but never authorizes an action.

The source-to-row path is:

1. `NativeCareerLayout::browserRows` builds current rows and compares each `(type,id)` against `browser_favorites` (`plugin/include/NativeCareerLayout.h:1453-1457,1537-1710`). The native menu publishes a stable row key plus type/id; selection includes the browser revision. `NativeMovieProtocol` rejects the wrong generation/revision or a row not in the published page and `chooseBrowser` re-resolves the row and compares its action, payload, enabled state, Workshop binding, and other fields before dispatch (`plugin/include/NativeMovieProtocol.h:147-183`; `NativeCareerLayout.h:655-685,1512-1522`). A stale click does not reuse an old package/action.
2. The browser favorite action contains only `{type,id}` (`NativeCareerLayout.h:662-667`). `Backend._toggle_browser_favorite` removes an exact existing pair without needing the source to still exist; for a new favorite it requires a current lesson, workshop row, or plugin row, then stores sanitized display metadata (`src/my_career_training/bridge.py:668-733`).
3. When current Workshop/Mods catalog rows do not contain a saved remote item, `_favorite_catalog_item` validates the saved type/id pair and reconstructs its canonical source URL from the provider namespace and numeric ID. `_catalog_item` uses that row only if it matches the requested source and ID exactly; it never trusts a saved URL (`bridge.py:581-666`).
4. Current metadata wins when the exact favorite key exists in the refreshed rows. If the item is absent, Native Favorites appends a saved snapshot row. An exact saved plugin ID remains `Check release`; a `steam_maps:<id>` or `bakkes_maps:<id>` favorite remains `Open source`; otherwise the row is `Unavailable` with “Refresh its source before opening it” (`NativeCareerLayout.h:1552-1598`). In either state, the favorite toggle remains available so the player can remove it; the primary action is checked separately and disabled when unavailable (`NativeCareerLayout.h:655-667`).

## Identity by item type

| Item | Persisted identity | What a refresh/update resolves | What is not pinned |
|---|---|---|---|
| Core lesson | `type=lesson`, ID is the lesson slug; native row key is `lesson:<slug>` | A live row with the same slug supplies current title and action. A removed slug falls back to the saved snapshot as `Unavailable`. | Lesson version, variant, difficulty, scenario, mirror, or order. A slug reuse would resolve to the current lesson under that slug. |
| Featured Custom Training pack | `type=lesson`, ID `pack:<pack-slug>` | Current row is refreshed from the bundled `training_packs()` table. It displays the current metadata for the stable pack slug. | The training code and listed rank are display metadata, not part of the favorite key. If the slug disappears/changes, the old row becomes unavailable. The pack action is currently disabled offline. |
| Curated Workshop reference | `type=workshop`, current catalog slug; source `workshop_id` is separate metadata | The bundled reference row remains if still in `content.py`; one exact installed package can be bound to the reference through `launch_id`. Current reference metadata takes precedence. | Map runtime compatibility, revision/content hash, and a distinct favorite for each rank/variant. Removing or changing the curated slug can strand the old slug favorite even if a package remains under a different ID. |
| Local Steam Workshop package | `type=workshop`, ID `steam:<folder-id>:<16-hex-token>`, where token hashes folder ID plus relative file path (`workshop.py:131-141`) | Same path yields the same identity, even if bytes at that path are updated; renamed/moved path yields a new ID. If missing and saved in `browser_favorites`, the old ID remains visible but unavailable. | Content/version hash. The favorite does not freeze the installed package contents. |
| Imported local package | `type=workshop`, ID `imported:<sha256>`; `content.py:152-185` computes SHA-256 from file bytes | Identical bytes map to the same identity; changed bytes produce a different identity. A saved old digest with no current file becomes unavailable. | A mutable alias that follows a renamed/replaced file. |
| Public Workshop/map listing | `type=workshop`, ID is namespaced `steam_maps:<numeric-id>` or `bakkes_maps:<numeric-id>` | If not on the current page after restart, canonical source resolution reconstructs the provider URL from the namespace and numeric ID. Its action is to open the public source page, not load the map. | Catalog version/content digest or a guarantee that the provider still serves that ID. A changed provider ID has no alias migration. |
| Public/community plugin | `type=plugin`, numeric provider ID | A current row refreshes current provider metadata. If absent, exact numeric ID can still route to “Check release” through lookup. That lookup checks the current release associated with the ID. | Release version, binary hash, owner/name alias, activation state, or install authorization. A plugin ID change does not retarget by title. |

Two Workshop favorite stores still coexist. `browser_favorites` is the typed, display-snapshot store. The optional legacy `workshop_favorites` is just a list of IDs consumed by `library_state` (`bridge.py:315-320,1229-1238`; `workshop.py:171-250`). When adding a currently found local item, the unified toggle also adds its ID to the legacy list. Removal clears an exact saved ID from either list even if the item is no longer discoverable (`bridge.py:679-733`). `library_state` filters the currently discoverable rows for the legacy Favorites tab; it does not synthesize tombstones from missing legacy IDs (`workshop.py:221-240`). Therefore a package favorited only through the legacy path can disappear after it is removed; the snapshot-based recovery behavior applies to entries in `browser_favorites`.

## Lessons, ranks, variants, and pack changes

Favorite identity names one base lesson, not one setup. The browser's `power-shots` row says “Choose rank” and routes to its lesson page (`NativeCareerLayout.h:1600-1616,1801-1831`). The selected Power Shots `scenario_id` and `difficulty` live separately in `lesson_scenarios["power-shots"]`; validation requires exactly those two keys (`training/scenario_setup.py:12-31`; `bridge.py:1371-1378`). Other lesson variants are separately stored by lesson ID in `lesson_variants` and passed to `configure_lesson` on start (`bridge.py:1419-1428,1789-1791`; `training/catalog.py:206-229`). A single favorite therefore opens the lesson using its current persisted setup; it cannot retain two Power Shots ranks/scenarios or two variants as separate bookmarks. Active shuffle order and mirror are session/run context, not favorite identity.

The six featured pack records are bundled static metadata with independent human-readable slugs and training codes (`training/packs.py:21-103`). The native pack host independently allowlists IDs/codes and pack rows are explicitly `Unavailable offline` (`NativeCareerLayout.h:1618-1632`; `NativeTrainingPackHost.h:23-35`). There is no background refresh that tracks upstream pack renames or code rotation. If the bundled title/code changes while the slug stays stable, the favorite follows current bundled metadata; the current host allowlist must also match before that experimental route can accept the pack. If the slug changes, the old favorite is a saved unavailable row. No rank/code distinction creates a second favorite.

## Ordering, focus, and refresh

Favorites are not displayed in favorite-add order when live rows exist. Native Favorites concatenates the current Lessons rows, then Workshop rows, then Mods rows; within each section it preserves the source row order. It deduplicates by `type:id`, then appends saved-only snapshots in `browser_favorites` insertion order (`NativeCareerLayout.h:1552-1599`). Local Workshop catalog rows use the bundled catalog order followed by discovered package order; public rows follow the fetched catalog order. There is no sort by title or favorite timestamp.

The native layout resets to Lessons, empty search, and offset zero on menu open; changing tabs or search also resets the row offset. Scroll increments a numeric offset, and each render clamps it to the new list size (`NativeCareerLayout.h:378-393,577-603,1732-1742`). The AS menu tracks the selected row by stable `selectedRowKey`; after a browser rebuild, it preserves that key if it is still in the returned window and moves its local window to keep that row visible. If the key is absent, `normalizeBrowserSelection` selects the first displayed row (`native_ui/menus/MctRootMenu.as:83,454-460,1852-1875,1886-1903`). So a rename with stable ID usually preserves selection and updates copy; a removal or reorder that moves the selected item outside the eight returned rows can move selection to the first displayed row. The saved state does not persist selected tab/scroll or a selected favorite identity; the AS menu's transient key can survive while the menu object remains alive if it also exists in the reset Lessons window.

## Test coverage and evidence gaps

Existing source tests cover live lesson favorite creation/removal and snapshot shape (`tests/test_bridge.py:753-765`), bounded save metadata with no action authority (`tests/test_storage.py:233-247`), legacy Workshop favorite filtering (`tests/test_workshop.py:89-110`), cached favorite-image rehydration (`tests/test_bridge_browser_images.py:248-280`), and native rank/pack favorite routes and stale browser generation handling (`plugin/tests/native_training_browser_tests.cpp:343-408,440-483`). The five favorite tests from the main agent were not repeated.

I found no focused test for the exact stale remote resolver path (`_favorite_catalog_target`, `_favorite_catalog_item`, `_catalog_item`) after a catalog page is gone or after restart; the image rehydration test does not exercise the action resolver. There is also no test for a removed local package remaining as a `browser_favorites` tombstone, legacy-only favorites after uninstall, ID reuse/change, plugin release version changes, or focus preservation/reset after a catalog reorder. These are unverified contracts, not observed failures. The repo has unit/source-level browser and stale-generation coverage, but no game acceptance from this pass.

Useful next acceptance cases are: (1) same remote ID with changed title keeps one favorite and refreshes displayed metadata; (2) same public ID absent from the current catalog page reopens only its canonical provider page or performs exact-ID release lookup; (3) removed local/imported file remains visible from the new snapshot store with a removal path and never loads; (4) an imported-byte change or local path change produces a distinct identity, while same-path Steam replacement is clearly presented as the current file; (5) removed lesson/pack shows cached context and can be removed without dispatch; (6) Power Shots favorite returns to the saved setup without implying a favorite-specific rank; (7) selection follows the same row key on refresh and visibly resets when that key disappears from the window.
